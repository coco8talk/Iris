## 任务 T0.1 · 中间件 + 观测栈一键起

**id**：T0.1 ｜ **所属模块**：M0 ｜ **优先级**：P0

**一句话目标**：让一条 `docker compose up` 把 8 个中间件/观测组件拉起并"就绪"。

**前置知识（≤2 新概念）**
- docker-compose：多容器编排 YAML，容器间用服务名互访。*Java 类比*：父 `pom.xml` + 多 module，但编排容器。📖 https://docs.docker.com/reference/compose-file/
- healthcheck + depends_on 就绪门：就绪探针 + 启动时序。*Java 类比*：Actuator readiness probe + 等依赖 healthy。📖 https://docs.docker.com/reference/compose-file/services/

### 🟢 第 1 段 · 复刻（读指定片段并跑通，先别改）
- **读什么**：官方 `docker/awesome-compose` 仓库里 **prometheus-grafana** 示例的 `compose.yaml`（📖 https://github.com/docker/awesome-compose ，示例目录名以仓库实际为准，需核实）。只读它的 `services:`、`volumes:`、`ports:` 三段。
- **跑什么**：原样 `docker compose up -d` 把它的 Prometheus+Grafana 跑起来，`curl localhost:9090/-/ready` 得 200。
- **目的**：先亲手证明"compose 起观测栈"这件事在你机器上能成，建立信心与参照物。

### 🟡 第 2 段 · 改造（把参照物改成本项目要的）
- 在复刻的基础上**加** Loki+Promtail+Alertmanager+Nacos+MySQL+Redis 六个 service。
- 把镜像 tag 全部锁成 **ARM64 精确版本**，写进 `docs/dependency-baseline.md`。
- 给每个中间件加 `healthcheck` + 下游 `depends_on: service_healthy`（参照物没有就绪门，这是你要补的第一处）。

### 🔴 第 3 段 · 自研（脱离参考，独立写一个同类）
- 不看参照物，**从空文件**写 `deploy/prometheus/prometheus.yml` 的 `scrape_configs`（先只抓 Prometheus 自身 `localhost:9090`）。
- 自己判断：哪些服务需要 healthcheck、探针命令写什么。写完对照官方 healthcheck 小节自查。

**落笔顺序**
1. 复刻官方样例并 `up -d` 跑通（第 1 段）。
2. `docker compose ps` 看基线状态。
3. 加服务 + 改 tag + 加就绪门（第 2 段）。
4. `curl localhost:9090/-/ready` 看报错→修就绪门。
5. 自研 scrape 配置并验证（第 3 段）。

**关键提示（≤3）**
- 复刻阶段**一行都别改**，先跑通再说，避免"改着改着不知道哪坏了"。
- 镜像必须 ARM64；Nacos 单机 `MODE=standalone`。
- 配置文件卷挂载。

**卡住降级路径（30 分钟没思路）**
- 回到第 1 段：确认原版样例能跑通——若原版都跑不通，是 Docker/网络问题，不是你的改动。
- 官方：awesome-compose 的 prometheus-grafana README；compose healthcheck 小节。
- 视频：docker-compose 覆盖弱（video-1 P7 仅 conda），以官方为主。
- 问 AI：「我在 docker/awesome-compose 的 prometheus-grafana 基础上加了 Loki，这是我的 diff（贴出），Loki 起不来报错 X，问题在哪一行？别重写整个文件。」

**真实 HTTP 验收（含异常路径）**
```bash
docker compose -f deploy/docker-compose.yml up -d && docker compose ps
curl -s localhost:9090/-/ready     # 200
curl -s localhost:3100/ready       # 200
# 异常：改错一个 tag → ps 显示 exited
```
判定特征：`ps` 全 running + 两 readiness 200。依赖真实服务：本机 Docker。

**完成判定**
- [ ] 第 1 段：官方样例原样跑通（Prometheus 200）
- [ ] 第 2 段：六个新服务 + 就绪门加上，`ps` 全 healthy
- [ ] 第 3 段：自研的 scrape 配置能抓到 Prometheus 自身 `up`
- [ ] baseline 记录全部精确 ARM64 tag，无 `latest`

## 任务 T0.2 · 被测系统接入 + 就绪门 + 冒烟闭环

**id**：T0.2 ｜ **所属模块**：M0 ｜ **优先级**：P0

**一句话目标**：把 prunus-mume 六服务 + 工具网关(M2从0新建) 接进同一网络，跑通"注入故障→Prometheus 看到信号"最小闭环。

**前置知识（≤2 新概念）**
- Nacos 是全链路总开关：pm 服务从它拉端口/数据源/Redis。*Java 类比*：Eureka + Spring Cloud Config 二合一。📖 https://nacos.io/docs/latest/quickstart/quick-start/ （需核实锚点）
- Prometheus 抓取模型：轮询 `/actuator/prometheus`；`query=up` 问 target 是否存活。*Java 类比*：巡检所有 Actuator 端点的监工。📖 https://prometheus.io/docs/prometheus/latest/getting_started/

### 🟢 第 1 段 · 复刻（读指定片段并跑通）
- **读什么**：prunus-mume 仓库自带的 IntelliJ 运行配置 `.run/*.run.xml` 与各服务 `application.yml` 的 `spring.config.import: nacos:...` 段（📖 就在 `/Users/silas/IdeaProjects/prunus-mume`）。看懂"它靠 Nacos 拉配置启动"。
- **跑什么**：先**只起 Nacos+MySQL+Redis + 一个** pm 服务（如 pm-user），`curl localhost:<pm-port>/chaos/status` 得 200。
- **目的**：先证明"单个 pm 服务能靠 Nacos 起来"，再谈六个一起。

### 🟡 第 2 段 · 改造（扩到全量 + 接观测）
- compose 追加其余五个 pm 服务 + 工具网关(M2从0新建)，全部 `depends_on` Nacos/MySQL/Redis 就绪。
- `prometheus.yml` 的 scrape 目标从"只抓自身"改成**抓 pm 各服务的 `/actuator/prometheus`**（服务名对齐真实值，需核实）。
- Promtail `docker_sd_configs` 采 pm 容器日志。

### 🔴 第 3 段 · 自研（脱离参考写就绪门脚本）
- **从空文件**写 `deploy/scripts/check-env.sh`：自己设计要打哪些 readiness curl、如何判定 PASS/FAIL、如何在 Nacos 挂时明确报"阻塞全链路"。写完自测 `docker stop nacos` 是否被它抓到。

**落笔顺序**
1. 复刻：只起 Nacos+DB+Redis+单 pm 服务并跑通（第 1 段）。
2. `curl /chaos/status` 看单服务是否活。
3. 改造：扩全量 + 接 Prometheus/Promtail（第 2 段）。
4. 自研 check-env.sh，`docker stop nacos` 验证它报阻塞（第 3 段）。
5. 恢复 Nacos，全链路 PASS。

**关键提示（≤3）**
- pm 端口在 Nacos，**先别硬编码**，用 `<pm-port>` 占位，M1 回填。
- `/chaos/status` 是 pm 自带钩子，最省事的"活着吗"探针。
- 先跑通单服务再扩全量，别六个一起调。

**卡住降级路径（30 分钟没思路）**
- 回第 1 段：单个 pm 服务能否靠 Nacos 起？不能 → 是 Nacos 配置集缺失，不是你 compose 的错。
- 官方：Nacos quick-start（需核实锚点）；Prometheus scrape 段。
- 视频：video-4 P11「Harness 项目整体结构」建立多组件拼装直觉（仅背景）。
- 问 AI：「pm-user 单独起时 `logs` 报读不到 Nacos 配置，我的 Nacos 里应该预置哪些 dataId？给我排查清单，不要直接给配置文件。」

**真实 HTTP 验收（含异常路径）**
```bash
curl -s "localhost:8848/nacos/v1/console/health/readiness"   # 200
curl -s localhost:<pm-port>/chaos/status                     # 200，无故障为 {}
curl -s 'localhost:9090/api/v1/query?query=up' | grep -o '"value"'  # 查到被测 up

```
判定特征：Nacos 200 + `/chaos/status` 可达 + Prometheus 查到 up。依赖真实服务：Nacos、prunus-mume、Prometheus。
