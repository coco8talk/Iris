一句话目标：写一个能按类型编号、按 §0.6 格式落盘、且复用 M5 防穿越校验的证据台账。

前置知识（≤2 新概念）

  • 证据台账（可回放取证）
    1. 每次工具取证，把"来源 + 摘要 + 关键摘录"写成一份带编号的 Markdown 文件。
    2. 结论不再靠 Agent 的记忆，而是靠引用编号支撑：报告里写 [EV-M-001]，任何人都能翻到那份文件复核。
    3. 这是 M9 反幻觉验收的地基——M9 的确定性预检就是去 evidence/ 里查这些编号存不存在。
    4. Java 类比：结构化的审计日志 + 附件，每条有唯一 id 可溯源。
    5. 📖（自研；格式见 00-execution-plan.md §0.6）
  • 落盘路径复用 M5 的 incident_dir()
    1. 证据只能写进 runs/incidents/{id}/evidence/ 子目录。
    2. 不要在这里再写一套路径校验——M5 的 paths.incident_dir() 已经做了"白名单正则 + resolve() 前缀比对"两层，直接用它当基目录。
    3. 本模块要新增的是文件名维度的校验：evidence_id 也是拼进路径的，同样要过白名单正则 ^EV-[MLTS]-\d{3}$。
    4. Java 类比：基目录的安全策略由平台层统一提供，业务层只负责自己那一段文件名的合法性。

🟡 第 1 段 · 改造（在 M5 的落盘地基上长出台账）

写 src/agent/evidence.py，签名先定死：

python
class EvidenceStore:
    """一次事故的证据台账，所有证据落在 runs/incidents/{incident_id}/evidence/ 下."""

    def __init__(self, incident_id: str) -> None:
        """基目录取自 M5 的 paths.incident_dir(incident_id)，路径安全由它保证."""

    def new_id(self, kind: Literal["M", "L", "T", "S"]) -> str:
        """按类型分配下一个编号：M=metrics / L=logs / T=trace / S=其他(cmdb/changes)。
        返回形如 'EV-M-001'。序号靠**扫描已有文件名**求最大值 +1，不能用内存计数器——
        进程重启（M5 的 kill-resume 是常态）后内存计数会归零，编号就乱了。"""

    def write(
        self,
        evidence_id: str,
        source: str,        # 取证来源，形如 "query_metrics(template=error_rate,service=pm-question,window=1800)"
        agent_role: str,    # 取证者角色，M7 恒为 "investigate"；M10 起是各 subagent 的角色名
        degraded: bool,     # 网关信封的 degraded 原样带进来，不许省
        truncated: bool,    # 网关信封 meta.truncated 原样带进来，不许省
        summary: str,       # ≤3 句的结论式摘要（"pm-question 的 p99 在 10:12 从 80ms 涨到 2.1s"）
        excerpt: str,       # 关键数据摘录，保留能支撑 summary 的最小片段，不要贴整个响应
    ) -> Path:
        """写一份证据文件并返回路径。文件格式 = YAML frontmatter + 正文，见下。"""

    def list_ids(self) -> list[str]:
        """列出本事故已有的全部证据编号，M9 的确定性预检和 M10 的 lead 摘要工具都用它."""

    def read(self, evidence_id: str) -> str:
        """读一份证据全文。M9 verify 的 LLM 段靠它拿到证据原文."""

证据文件格式（§0.6）：

markdown

🔴 第 2 段 · 自研（编号与文件名的安全校验）

从空文件写校验：

  1. evidence_id 必须匹配 ^EV-[MLTS]-\d{3}$，否则抛 ValueError——它会被拼进文件名，属于路径的一部分；
  2. 最终写入路径 resolve() 后必须仍在 incident_dir(incident_id) 之内（M5 的基目录校验挡住了 incident_id，这一层挡住 evidence_id）；
  3. 自测三种攻击都被拒：../../etc/passwd、绝对路径 /tmp/x、指向外部的软链。

落笔顺序

  1. 1
    写 EvidenceStore.__init__ + new_id，先只做编号，不落盘。
  2. 2
    连续 new_id("M") 两次，确认拿到 EV-M-001/EV-M-002；再 new_id("L") 确认是 EV-L-001（按 kind 分别递增，别混）。
  3. 3
    写 write，落一份带 frontmatter 的文件，肉眼核对 6 个 frontmatter 字段齐全。
  4. 4
    重启进程再 new_id("M")，确认拿到的是 EV-M-003 而不是 EV-M-001（证明是扫文件不是内存计数）。
  5. 5
    自研校验：用 EV-M-../x、/tmp/x、软链三种输入各试一次，确认都抛异常且没落盘。
  6. 6
    写 list_ids/read，供 M9 使用。

关键提示（≤3）

  • 编号按 kind 分别递增（M/L/T/S），别用一个全局计数器。
  • new_id 扫文件而不是内存计数——M5 的 kill-resume 会让内存计数器归零。
  • 这个类是 M9（预检查编号）/M10（subagent 共用台账）的共同依赖，格式即契约，先定死再往下走。

卡住降级路径（30 分钟没思路）

  • 编号乱：确认 new_id 是扫已有文件名求最大值，且扫的是本 incident 目录不是全局。
  • 校验没生效：确认比较的是 Path.resolve() 之后的对象前缀关系，不是字符串 startswith（软链靠字符串比对挡不住）。

任务 T7.2 · 接入剩余 4 个模板工具

前置知识（≤1 新概念）

    1. @tool 装饰器只是把函数变成一个可被模型调用的对象；模型能不能看见它，取决于有没有出现在 bind_tools([...]) 或 create_agent(tools=[...]) 的列表里。

    4. Java 类比：写了 Feign 接口不等于联调过；上线前每个接口都得真打一次。

    5. 📖 https://docs.langchain.com/oss/python/langchain/agents （create_agent，需核实锚点）· video-2 P10-16「创建 Agent·定义工具」

    1. 给 Agent 一个 record_evidence 工具，让它主动登记；比从它的输出里正则抠可靠得多。

🟡 第 1 段 · 改造（把节点换成 Agent）

python
class RcaReport(BaseModel):
    """单 Agent（或 M10 的 lead）产出的根因分析结论。M7 产出，M8 只渲染不重定义."""

    root_service: str        # 根因服务名，必须是 CMDB 里的真实服务名；M12 判分的 acc@service 比对它
    root_cause: str          # 根因分类，用短语而非长句（如 "slow_query" / "threadpool_exhausted"）；判分的 acc@class 比对它
    root_detail: str         # 根因细节：具体是哪条 SQL / 哪个池 / 哪次配置变更
    confidence: Literal["high", "medium", "low"]  # 置信度；M8 在验收 fail 或预算耗尽时会强制降为 low
    causal_chain: list[str]  # 因果链，从根因到告警现象的有序步骤，每步一句话
    evidence_ids: list[str]  # 本结论引用的全部证据编号，必须都能在 evidence/ 里找到（M9 预检就查这个）
    summary_md: str          # 给人读的摘要 Markdown；**只有这个字段允许 M8 的 LLM 润色**
    remediation: str | None = None  # 修复建议；M12 的审批与执行以它为输入，慢查询类只准建议人工处理

任务 T7.4 · raw 通道接入（受限逃生舱）

id：T7.4 ｜ 所属模块：M7 ｜ 优先级：P1

一句话目标：把 query_metrics_raw / query_logs_raw 作为独立预算 + 独立审计的受限能力接进 Agent，而不是和 4 个模板工具混在一起。

前置知识（≤1 新概念）

  • raw 通道为什么要单独对待
    1. 能力不同：模板工具的表达式是网关写死的，raw 通道让模型自己写 PromQL/LogQL——表达力大得多，出事的方式也多得多。
    2. 预算不同：网关侧模板通道 40 次、raw 通道 5 次，是两个独立计数器（M2 契约）；M4 的 BudgetLedger 也是分开的 tool_calls_used / raw_calls_used。
    3. 护栏不同：raw 查询必须含至少一个 label selector，否则网关直接 403 NOT_WHITELISTED（防无范围全表扫）。
    4. 审计不同：网关 audit_log 的 template_or_raw 字段标 raw，用于事后高亮"这次诊断里模型自己写了什么查询"。
    5. 📖（M2 docs/tool-contract.md 的 raw 章节；00-execution-plan.md §M2）

🟡 第 1 段 · 改造（新写 logql raw + 一起接入）

  1. 新写 make_query_logs_raw（definetions.py 里目前只有 make_query_metrics_raw，logql 侧完全没有）。照 QueryMetricsRawInput 的同一套写法：
    • query: str——原始 LogQL，description 里必须写明"表达式中必须含至少一个 label selector，否则网关 403"；
    • service / window / end_offset_seconds 三个参数与 query_metrics_raw 保持一致的语义；
    • docstring 明确定位：模板工具 query_logs 覆盖不了时才用。

    命名说明：00-execution-plan.md 里叫 raw_promql/raw_logql，真实代码里 M3 已经把前者写成了 query_metrics_raw，为保持一致本项目统一用 query_metrics_raw/query_logs_raw。

  2. registry.make_raw_tools(client) 返回这两个，和 make_template_tools 分开两个函数（M10 的 subagent 要按域挑，logs-investigator 拿 query_logs + query_logs_raw，metrics-investigator 只拿 query_metrics）。
  3. Agent 的 tools 列表改成 make_template_tools(c) + make_raw_tools(c)，并在 system prompt 里单独加一节：
    • "raw 通道全事故只有 5 次，模板工具能表达的一律走模板"；
    • "写 raw 查询时必须带 label selector（如 {service="pm-question"}）"；
    • "用了 raw 通道的证据，source 字段要原样记录你写的表达式"。

🔴 第 2 段 · 自研（独立预算计数 + 审计核对）

  1. raw 工具的返回路径上调 guard.charge_tool_call(ledger, envelope, raw=True)——走 raw_calls_used 而不是 tool_calls_used（M4 已经把字段分开了，这里是它第一次真正被用到）；
  2. check_budget 里 raw 维度触顶只应该拦 raw 工具，不能把模板工具一起拦掉——写一个按通道分别判断的分支，并真实验证：连打 6 次 raw 后模板工具仍然可用；
  3. 事后核对网关审计：select template_or_raw, count(*) from audit_log where incident_id=? group by 1，raw 的条数应与本地 raw_calls_used 一致。

落笔顺序

  1. 1
    新写 make_query_logs_raw 的 args_schema + @tool。
  2. 2
    REPL 里各真打一次两个 raw 工具（带 label selector），确认返回真数据。
  3. 3
    故意打一条不带 label selector 的查询，确认网关 403 且错误可读。
  4. 4
    接进 Agent 的 tools 列表，补 system prompt 的 raw 那一节。
  5. 5
    接 charge_tool_call(raw=True)，连打 6 次验证第 6 次被拦、且模板工具此时仍可用。
  6. 6
    跑一次完整事故，核对网关审计里 raw 条数与本地计数一致。

关键提示（≤3）

  • raw 的预算和模板的预算是两个计数器，别共用一个；拦截也要分开拦，否则 raw 用超了会把整轮诊断废掉。
  • 网关的 403 NOT_WHITELISTED 是硬护栏，但 prompt 里也要写清规则——让模型第一次就写对，比让它撞墙再重试省预算。
  • 用了 raw 的证据，source 里要留下模型写的原始表达式，这是事后审计"它到底查了什么"的唯一线索。

卡住降级路径（30 分钟没思路）

  • raw 一直 403：把表达式打出来看有没有 label selector；网关的校验是静态的，{} 空 selector 也算没有。
  • raw 预算把模板一起拦了：check_budget 需要知道"这次要走哪个通道"，把通道作为参数传进去，别只看 ledger。
  • 视频：无对口视频，以 M2 的网关契约文档为主。
  • 问 AI：「我有两个独立预算的工具通道（模板 40 次 / raw 5 次），怎么设计一个 guard 让 raw 用尽时只拦 raw、不影响模板通道？给结构。」
