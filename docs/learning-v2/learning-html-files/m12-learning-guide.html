模块 12 · /actions 修复 + HMAC 审批 + HITL + 评估兜底 — 版本 C

编排理念：🟡在本项目真实代码上改造（在 M5 建的 FastAPI 上加审批 API；在 M2 的网关上加与查询通道物理隔离的 /actions）→ 🔴自研一次性令牌与纯函数判分。修复永远过人工审批——这是核心叙事不是缺陷。

本模块的能力边界（先对齐）

  • 入口/审批 API 都在 M5 建的那个 FastAPI 上，端口 8000；网关是 M2 的 Spring Boot 工程，两者不要混。
  • interrupt() 能挂起并恢复，靠的是 M5 T5.2 已经接好的 AsyncSqliteSaver（thread_id = incident_id）。本模块不重新搭 checkpointer，只是第一次真正用到它最关键的场景：挂起数小时甚至跨进程重启。
  • /actions/execute 是本模块新接入的能力，它不是 M7 那 7 个只读工具中的任何一个：不走模板/raw 预算、不进 audit_log，而是独立的 action_audit 表。M7 的 Agent 永远拿不到它——只有 remediate 节点在拿到审批令牌后才能调。
  • IncidentState.approval / remediation_result 是 M4 留的占位字段（dict | None），本模块定义它们的真实模型并把类型收紧。
  • 评估只测诊断不真修复：runner 自动驳回审批，revert 由 runner 自己做——否则一轮评估会把被测系统改得面目全非。

学完本模块你能做到的 3 件事

  1. 建出与查询通道物理隔离的 /actions 修复通道：HMAC 一次性令牌 + dry-run + 白名单，无有效令牌一律 403。
  2. 用 LangGraph interrupt() 实现"挂起等人工审批 → 批准即签发令牌 → 执行后复查恢复"的闭环，且挂起期间 kill 进程重启仍能 resume。
  3. 用纯函数判分 + runner + make smoke 门禁量化诊断效果（不写单测台账）。

任务 T12.1 · /actions 通道 + HMAC 一次性令牌 + HITL 审批

id：T12.1 ｜ 所属模块：M12 ｜ 优先级：P0

一句话目标：建修复通道与人在环审批：挂起可跨进程恢复、批准即签发一次性令牌、执行前先 dry-run。

前置知识（≤2 新概念）

  • HITL interrupt() 审批
    1. 图执行到 approval 节点时 interrupt(payload) 挂起，payload 是给人看的"要批什么"（动作 + 目标 + dry-run 预演结果）。
    2. 人做决定后用 Command(resume=decision) 恢复，图从 interrupt 处继续。
    3. 挂起状态存在 checkpointer 里（M5 已接），所以"挂起 → kill uvicorn → 重启 → approve → 继续"是可行的；如果 M5 那步没做，interrupt 只是个进程内的暂停，重启就没了。
    4. Java 类比：审批流走到审批节点挂起，等人点"同意"才继续，状态靠持久化保住。
    5. 📖 https://docs.langchain.com/oss/python/langchain/human-in-the-loop （interrupt，需核实锚点）· video-2 P71-74「人工介入·审批·中断」
  • HMAC 一次性令牌
    1. 签名：批准时用共享密钥签一个含 payload 的令牌，网关验签，防伪造。
    2. 过期：payload 里带 iat/exp，超时作废，防令牌被囤积。
    3. 一次性：payload 里带 nonce，网关侧"插入即消费"，第二次提交同一令牌直接 403，防重放。
    4. 常量时间比较：验签用 hmac.compare_digest，不要用 ==（防时序侧信道）。
    5. Java 类比：一次性支付令牌——签名防伪、过期作废、用过即失效。
    6. 📖 https://itsdangerous.palletsprojects.com/ （签名+过期）+ https://docs.python.org/3/library/hmac.html （compare_digest）

🟡 第 1 段 · 改造（在真实网关和真实 FastAPI 上开这条通道）

  1. 网关侧 ActionController：POST /api/v1/actions/execute
    • action 枚举四个：restart_container / kill_slow_query / revert_config / disable_chaos_flag；
    • target 白名单从 prunus-mume 实际服务名 + redis 推导 [R10]（M1 已勘察，不要手编一份服务名列表）；
    • dryRun=true：只需服务 token，返回预演（"将要对 X 执行 Y，当前状态是 Z"），不改任何东西；
    • dryRun=false：额外要求 approval 令牌，验不过一律 403；
    • revert_config 的 Nacos dataId/group 从 prunus-mume 实际约定映射（M1 已勘察）；
    • 独立审计表（与只读工具的 audit_log 分开）：
      sql
      CREATE TABLE action_audit (
    id                BIGINT PRIMARY KEY,
    ts                TIMESTAMP NOT NULL,
    incident_id       VARCHAR(64) NOT NULL,
    action            VARCHAR(32) NOT NULL,
    target            VARCHAR(128) NOT NULL,
    dry_run           BOOLEAN NOT NULL,
    token_fingerprint VARCHAR(64),   -- 令牌的哈希前缀，不存令牌本身
    result            VARCHAR(16) NOT NULL,  -- ok | rejected | error
    detail            TEXT
);
  2. Agent 侧 nodes/approval.py：
    • 进 interrupt() 之前先调一次 dry-run，把预演结果放进 interrupt payload——让审批人看到的是"会发生什么"，不是"模型说要干什么"；
    • interrupt payload 字段：incident_id / root_service / root_cause / remediation（来自 M7 的 RcaReport）/ action / target / dry_run_preview / evidence_ids。
  3. 审批 API 加进 M5 的 app.py（不新起服务）：
    • GET /incidents/{id}/pending → 返回该事故的 interrupt payload；
    • POST /incidents/{id}/decision → body {approved: bool, reason: str, operator: str}，内部签发令牌（approved 时）并用 Command(resume=...) 恢复图；
    • 恢复走的是 M5 已有的 resume_incident_run，只是 input 从 None 换成 Command(resume=decision)。
  4. CLI cli.py：copilot list / copilot approve <id> [--reason] / copilot reject <id> --reason，就是上面两个 HTTP 接口的薄封装。

先在 state.py 里补上本模块的两个模型（M4 留的占位）：

python
class ApprovalDecision(BaseModel):
    """人工审批结论，由 POST /incidents/{id}/decision 写入 IncidentState.approval."""

    approved: bool
    operator: str        # 审批人标识，进 action_audit 和案例 Markdown 的"人工备注"
    reason: str          # 批准/驳回理由；驳回时它是 M11 案例归档里最有价值的一段
    decided_at: float    # epoch 秒
    token_fingerprint: str | None = None  # 签发令牌的哈希前缀（approved 时），便于与网关审计对账


class RemedyOutcome(BaseModel):
    """修复执行与复查结果，由 remediate 节点写入 IncidentState.remediation_result."""

    action: str          # 实际执行的动作
    target: str          # 实际目标
    executed: bool       # 是否真的执行了（dry_run 或被拒时为 False）
    recovered: bool | None  # 60s 后复查是否恢复；未复查/无法判定时为 None，**不许默认 True**
    metric_before: float | None  # 复查用的基线值（告警前窗口）
    metric_after: float | None   # 执行后的值
    escalate: bool = False       # 未恢复时置 True，交人工升级，不自动重试
    detail: str = ""

🔴 第 2 段 · 自研（一次性令牌两侧实现）

Agent 侧 security.py（从空文件写）：

  1. itsdangerous.URLSafeTimedSerializer 签发，payload 逐字照 §0.5：ver / iss / aud / iat / exp / kid / nonce / incident_id / action / target；
  2. nonce 用 secrets.token_urlsafe(16)，签发时同步落本地表（便于对账），消费判定在网关侧；
  3. token_fingerprint = sha256(token)[:16]，只存指纹不存令牌。

网关侧 ApprovalTokenVerifier（从空文件写），五道全过才放行：

  1. 验签（hmac.compare_digest，常量时间）；
  2. exp 未过期；
  3. aud/iss/kid 匹配；
  4. nonce 未被消费——靠 DB 唯一约束"插入即消费"实现，不要"先查再插"（并发下会漏）；
  5. 令牌里的 incident_id/action/target 与本次请求体逐字一致（防令牌被挪用到别的目标）。

任一失败 → 403 + action_audit 落一条 result='rejected'（被拒也要审计，否则攻击尝试无痕）。

落笔顺序

  1. 1
    网关先只做 dryRun=true 分支（不验 approval 令牌），curl 一次拿到预演，确认通道通了。
  2. 2
    Agent 侧写 approval.py 的 interrupt()，跑一次真实事故到挂起，GET /incidents/{id}/pending 看得到 payload。
  3. 3
    写 decision 接口 + CLI，先只做"驳回"路径（不涉及令牌），确认图能恢复并走到 report。
  4. 4
    自研 security.py 签发 + 网关 ApprovalTokenVerifier 验证，跑通"批准 → 带令牌 → dryRun=false 执行"。
  5. 5
    逐个测四种攻击：无令牌 / 伪造签名 / 过期 exp / 重放 nonce，全应 403 且落审计。
  6. 6
    测挪用：拿 incident A 的令牌去执行 incident B 的动作 → 403。
  7. 7
    测跨进程：挂起后 kill uvicorn，重启，copilot approve 仍能 resume。

关键提示（≤3）

  • 修复与查询通道物理隔离：/actions 不计入只读工具预算、独立审计表、Agent 的 tools 列表里永远没有它。
  • nonce 一次性靠 DB 唯一约束"插入即消费"，别写成"先 select 再 insert"——并发重放会从缝里钻过去。
  • dry-run 仍需服务 token，只豁免 approval 令牌；"dry-run 完全不鉴权"会变成一个免费的内网探测接口。

卡住降级路径（30 分钟没思路）

  • resume 不生效：确认 checkpointer 持久化（M5 那步）、thread_id 是 incident_id、resume 传的是 Command(resume=...) 而不是完整 state。
  • 挂起后进程重启就找不到了：多半是 interrupt 发生在 checkpointer 写盘之前，确认用的是持久化 saver 不是 InMemory。
  • 令牌总是验不过：先把两侧的 payload 各打一次对字段，kid/aud 这种拼写差异最容易漏。
  • 视频：video-2 P72-73「用户审批工具的执行·人工填写审批理由」最贴近。
  • 问 AI：「LangGraph interrupt 挂起后，我 kill uvicorn 重启，用 CLI 发 resume 还能继续吗？我的 checkpointer 和 Command(resume=...) 这样写（贴出），对不对？」

任务 T12.2 · remediate 复查 + 评估兜底（判分 + runner + smoke 门禁）

id：T12.2 ｜ 所属模块：M12 ｜ 优先级：P1（工程化收尾）

一句话目标：执行修复后复查是否真的恢复，并用纯函数判分 + smoke 门禁把"诊断效果"变成可回归的数字。

前置知识（≤2 新概念）

  • 修复复查（动作 → 指标映射）
    1. 带令牌执行动作后等 60s，按"动作 → 该看哪个指标"的映射复查（revert_config → error_rate 回基线；restart_container → 实例 up + p99 回落）。
    2. 基线取"告警前"窗口，不能拿当前值当基线——当前值本来就是坏的，跟自己比永远"恢复了"。
    3. 复查用的是 M7 已接入的 query_metrics，不需要新端点。
    4. 判定阈值：恢复到基线的 2 倍以内算 recovered；判不出来一律 recovered=None + escalate=True，不许默认 True。
    5. Java 类比：发布后跑一次健康检查确认恢复，没恢复就升级，不谎报。
  • 纯函数三级判分
    1. svc_hit：report.root_service == truth.root_service；
    2. cls_hit：report.root_cause 归一化后 == truth.fault_class；
    3. anchor_hit：report.root_detail 或 causal_chain 里是否命中真值给的关键锚点（如具体 SQL 片段、具体 dataId）；
    4. negative_ok：阴性对照案例（不该告警的背景变更）是否没有被判成故障。
    5. 全部是确定性比对，零波动、无 LLM judge。
    6. Java 类比：断言式比对，输入相同结果永远相同。

🟡 第 1 段 · 改造（写 remediate 与 scorer）

  1. nodes/remediate.py：
    • 带 approval 令牌 execute（dry_run=false）；
    • 等 60s → 按映射表调 query_metrics 复查 stats.last vs 基线；
    • 写 RemedyOutcome 回 state；未恢复 → escalate=True，不自动重试（自动重试是把一个可控问题变成不可控的最快方式）。

🔴 第 2 段 · 自研（runner + smoke 门禁）

从空文件写 evals/runner.py，一条案例的循环：

  1. 注入故障（prunus-mume 的 /chaos/register/{name} 或外部手段，见 M1 的 fault-catalog）；
  2. 等 Alertmanager 出告警（超时上限，超了记这条案例失败而不是卡死）；
  3. webhook 进来跑诊断；
  4. 自动驳回审批——评估只测诊断，不真修复；
  5. runner 自己 revert 故障（用它自己的凭证，不走 Agent 的 /actions）；
  6. score(...) 判分，追加一行 JSONL（含 skills.versions()、消融开关状态、模型名——事后才知道这一轮是什么配置跑出来的）。

Makefile 的 make smoke：5 例 < 15min，读 evals/gate.py 里的 baseline，acc@service 低于 baseline 就退出码 1。

关键提示（≤3）

  • 慢查询类故障只输出"人工补索引/升级"建议，不得把 kill_slow_query 当根因修复，不得谎报 recovered=True——杀掉一条慢查询不等于修好了那条缺索引的 SQL。
  • 判分是纯函数、零波动，不用 LLM judge：评估结果要能回归对比，波动的判分器毁掉整个对比的意义。
  • 真值 YAML 必须在 Agent 读不到的地方；顺手 grep 一遍确认没有哪个 Skill 或知识库路径指向它。

卡住降级路径（30 分钟没思路）

  • 复查判定不稳：确认基线取的是"告警前"窗口，别用当前值当基线；再确认 60s 够不够该动作生效（配置回滚快、容器重启慢）。
  • runner 卡在等告警：给等待加上限，超时记为该案例失败并继续下一条，别让一条案例挂死整轮。
  • 判分老是 0：把归一化后的 root_cause 和真值的 fault_class 都打出来对，多半是同义词没归一（slow_query vs slow-query）。
  • 视频：video-2 P61-64「评估器案例」讲评估思路（本项目判分用纯函数非 LLM）。
  • 问 AI：「我要写一个纯函数判分器，比对报告的 root_service/root_cause 与真值 YAML，acc@service/acc@class 怎么算？给函数签名 + 5 组测试用例。」
