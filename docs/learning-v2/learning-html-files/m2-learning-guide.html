  1. 从零建一个干净的 Spring Boot 工具网关，把 5 个只读工具（metrics/logs/trace/cmdb/changes）打到真实 Prometheus/Loki/Tempo 并返回统一信封。

  3. 让 raw 逃生通道受控（强制 label selector + 独立预算），并让工具 service 参数从 Nacos/CMDB 动态校验。

任务 T2.1 · 网关骨架 + 第一个工具 query_metrics

id：T2.1 ｜ 所属模块：M2 ｜ 优先级：P0

一句话目标：从空工程建出带鉴权/信封/审计的网关骨架，并让第一个工具 query_metrics 打通真实 Prometheus。

前置知识（≤2 新概念）

  • 统一响应信封 ApiEnvelope + degraded 语义（H3）：所有工具返回 {ok,degraded,degraded_reason,data,meta{elapsed_ms,truncated,budget_remaining}}；仅上游超时/不可用返回 200+degraded:true，网关自身错误必须 5xx。Java 类比：就是你熟的 Result<T> 统一包装，只是多了 degraded 一等字段，且明确区分"上游挂了(降级)"vs"我代码错了(500)"。📖 https://spring.io/guides/gs/rest-service/ （REST 返回体，你已会）
  • Prometheus HTTP query API：GET /api/v1/query_range?query=<PromQL>&start=&end=&step=。Java 类比：一个普通的 REST 上游，用 RestClient 调，超时降级像 Feign fallback。📖 https://prometheus.io/docs/prometheus/latest/querying/api/ （range queries 小节）

🟢 第 1 段 · 复刻（跑通官方样例，先别包装）

  • 读什么：Spring 官方 gs/rest-service guide（你已熟，快速过）；Prometheus HTTP API 文档的 query_range 段。
  • 跑什么：先用 curl 裸打一次真实 Prometheus query_range（用 M1 勘察到的真实指标名），确认 PromQL + 上游能通——先证明数据源可查，再谈网关。

🟡 第 2 段 · 改造（把裸查询包成工具端点）

  • 用 Spring Initializr 建 tool-gateway 工程；写 MetricsController POST /api/v1/tools/query_metrics（入参 {template,service,window,compareBaseline}）→ PrometheusClient（RestClient 调 query_range，超时 5s 返回 degraded）→ 降采样 ≤30 点 → 包 ApiEnvelope 返回。
  • MetricsTemplateRegistry：把 PromQL 模板化（qps/error_rate/p99/... 对齐 M1 勘察到的真实指标名）。

🔴 第 3 段 · 自研（写横切面）

  • 从空文件写 AuthInterceptor（校验 Authorization: Bearer + 必带 X-Incident-Id/X-Agent-Role，缺失 400）、GlobalExceptionHandler（参数错→400，上游不可用→200 degraded，未知→500）、AuditService（每次调用落 audit_log）。

落笔顺序

  1. 1
    复刻：curl 裸打 Prometheus query_range 成功。
  2. 2
    改造：Initializr 建工程，写 query_metrics 端点（先直接返回上游原始 JSON）。
  3. 3
    发一次请求看报错：curl 打网关 query_metrics，无鉴权 → 应 401（还没写拦截器 → 先看到"裸奔"）。
  4. 4
    自研：加 AuthInterceptor + ApiEnvelope + 审计。
  5. 5
    再请求：带 token 打通，拿到统一信封 + 审计落库。

关键提示（≤3）

  • degraded 与 500 的界线是灵魂：上游问题→降级 200；自己代码/解析问题→500。
  • 异常判断（阈值/降采样）是确定性代码，绝不进 LLM。
  • X-Incident-Id+X-Agent-Role 是 Agent 侧调用的强制契约，缺失即 400。

卡住降级路径（30 分钟没思路）

  • 打不通上游：先 curl 裸 Prometheus 确认上游本身能查（排除 M0/M1 接线问题）。
  • 视频：video-2 P48-57 讲 MCP——本项目走 HTTP 网关非 MCP，跳过，别被带偏。
  • 问 AI：「我用 Spring Boot RestClient 调 Prometheus query_range，超时想返回 degraded 而非抛 500，异常处理该怎么分层？给结构不要整段代码。」

真实 HTTP 验收（含异常路径）

bash
BASE=localhost:8090/api/v1/tools
H='-H "Authorization: Bearer $TOOL_GATEWAY_TOKEN" -H "X-Incident-Id: t-001" -H "X-Agent-Role: metrics"'
curl -s $BASE/query_metrics -XPOST $H -d '{"template":"error_rate","service":"<pm-svc>","window":"30m"}'  # ok:true,data 有真实值
curl -s $BASE/query_metrics -XPOST -d '{...}'  # 无 token → 401
docker stop prometheus; curl -s $BASE/query_metrics -XPOST $H -d '{...}'  # 上游挂 → degraded:true, HTTP 200

判定特征：带 token 正常 ok:true 真实数据；无 token 401；停 Prometheus 后 degraded:true 非 5xx；audit_log 落行。依赖真实服务：Prometheus。

完成判定

任务 T2.2 · 其余 4 工具 + raw 逃生通道 + 预算护栏

id：T2.2 ｜ 所属模块：M2 ｜ 优先级：P0

一句话目标：仿照 query_metrics 的三件套建出 logs/trace/cmdb/changes，加 raw 通道与 per-incident 预算。

前置知识（≤2 新概念）

  • raw 逃生通道 + 静态白名单校验（H1）：模板覆盖不到时允许受控裸 PromQL/LogQL，但强制 label selector、限长、独立预算。Java 类比：给危险的动态查询加参数校验切面，不合规直接 403。📖 https://grafana.com/docs/loki/latest/query/ （LogQL 语法，需核实锚点）
  • per-incident 预算限流（H5）：同一 incident 模板通道 40 次、raw 通道 5 次上限，超限 429。Java 类比：按业务 key 计数的限流，一张 SQLite 表就够，不必上 Bucket4j。📖（自研；参考网关限流思想）

🟢 第 1 段 · 复刻（读你自己刚写的三件套）

  • 读什么：T2.1 写的 MetricsController→PrometheusClient→模板 三件套，作为"controller→client→聚合"的自有模板。
  • 跑什么：再打一次 query_metrics，确认你彻底吃透了这套结构（复刻自己的成果）。

🟡 第 2 段 · 改造（套模板出 4 个工具）

  • 照模板建 query_logs（LokiClient + PatternAggregator 模板行聚合 + traceId 提取）、query_trace（ZipkinClient + 树精简，深 ≤3）、query_cmdb（从 Nacos 拉服务拓扑）、query_changes（变更事件表）。
  • service 校验从常量集改为查 CMDB 动态解析 [R3]。

🔴 第 3 段 · 自研（写 raw 校验器 + 预算）

  • 从空文件写 RawQueryValidator：长度 ≤500；LogQL 必须匹配 ^\s*\{[^}]+\}（强制 selector）；PromQL 必须含 label matcher；违规 403。写 BudgetService（SQLite 计数，模板 40/raw 5，超限 429）。

落笔顺序

  1. 1
    复刻读自己写的三件套。
  2. 2
    改造出 logs/trace/cmdb/changes（先返回假 data 跑通 controller）。
  3. 3
    发请求看报错→填真实上游调用。
  4. 4
    自研 RawQueryValidator + BudgetService。
  5. 5
    打合法/非法 raw、连打 41 次验证 403/429。

关键提示（≤3）

  • raw 独立预算（5/incident）与模板预算（40/incident）分开计。
  • pattern 聚合 / trace 树精简都是纯函数，不进 LLM，也别引 Drain 类库（KISS）。
  • 审计里 raw 调用标 template_or_raw='raw' 便于高亮。

卡住降级路径（30 分钟没思路）

  • Loki/Zipkin 查不到：确认 M1 的日志/tracing 接线真的上报了（裸 curl 上游 API 看有无数据）。
  • 视频：video-2 P58-64 WorkFlow/评估器与本任务无关，跳过。
  • 问 AI：「我要写 LogQL 校验器，强制查询必须带 {label} selector，正则怎么写才不误杀合法查询？给正则 + 3 个应通过/应拒绝用例。」

真实 HTTP 验收（含异常路径）

bash
curl -s $BASE/query_logs -XPOST $H -d '{"service":"<pm-svc>","window":"30m","level":"ERROR"}'   # patterns + lines
curl -s $BASE/query_trace -XPOST $H -d '{"template":"find_slow_traces","service":"<pm-svc>","window":"30m","min_duration_ms":500}'  # top_spans
curl -s $BASE/raw/promql -XPOST $H -d '{"query":"sum(http_server_requests_seconds_count)","window":"30m"}'  # 403：无 selector
# 同 incident 连打 41 次 query_metrics → 第 41 次 429

判定特征：4 工具真实返回；无 selector 的 raw → 403 附原因；第 41 次模板/第 6 次 raw → 429。依赖真实服务：Loki、Tempo/Zipkin、Nacos。
