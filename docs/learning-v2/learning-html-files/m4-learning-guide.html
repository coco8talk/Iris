模块 4 · 状态对象 + 条件边/回流 + 预算 guard — 版本 C

编排理念：🟡在本项目真实代码上改造（M3 的 dataclass State → IncidentState；单节点两条静态边 → 三节点条件边回流）→ 🔴自研 guard 与引用式落盘约定。旧计划把这些塞进一个 T31，本模块按"先状态对象 → 加回流 → 加 guard"拆开，每步单独可验。

本模块的能力边界（先对齐，免得写出跑不起来的验收）

  • 运行方式：仍然是 langgraph.json + langgraph dev（LangGraph Server 托管），默认端口 2024。本模块没有自建 FastAPI，所以任何 localhost:8000/... 的命令在这里都是假的。
  • 自建 FastAPI（端口 8000）+ checkpointer 断点续跑挪到 M5：M5 要接 Alertmanager 的 POST /webhook/alertmanager，那是第一个必须自己起 uvicorn 的时点；AsyncSqliteSaver、thread_id = incident_id、runs/checkpoints.db、kill-重启续跑的验收都跟着放在 M5 的 FastAPI 之后。M4 不学 checkpointer——在 LangGraph Server 托管模式下 persistence 由 Server 自己管，此时给 compile(checkpointer=...) 传自定义 checkpointer 会直接报错，学了也落不了地。
  • 工具：本模块工具集不变，仍然只有 query_metrics 一个真实接入。其余 6 个（query_logs/query_trace/query_cmdb/query_changes/raw_promql/raw_logql）在 M7 接入，本模块的任何一步都不许假设它们已经能用。
  • 入口输入：incident_id/service 由 langgraph dev 的 run input 直接给（M5 起才改由 webhook 写入）。

学完本模块你能做到的 3 件事

  1. 设计出贯穿全流程的 IncidentState，说清每个字段由哪个节点写、用什么 reducer 合并，并让大文本走"落盘 + state 只存 *_ref 引用"的约定。
  2. 用条件边写出 verify → investigate 的回流（最多 2 轮），并能在一次真实运行里看出它走了哪个分支、回流了几轮、为什么停。
  3. 写出"调用粒度"的预算 guard：在每次 LLM 调用和每次网关工具调用处累计并检查预算，超限时用 Command(goto="report") 优雅收口而不是抛栈崩掉。

任务 T4.1 · 正式状态对象 IncidentState

id：T4.1 ｜ 所属模块：M4 ｜ 优先级：P0

一句话目标：把 M3 写在 graph.py 里的临时 dataclass State 抽成独立文件里的正式 IncidentState，字段覆盖全流程，大文本一律只存引用。

前置知识（≤2 新概念）

  • IncidentState（TypedDict）+ Reducer
    1. State：整条事故流程共享的状态字典，每个节点读它、返回"要更新的字段"。
    2. Reducer：决定同一字段被多次写入时怎么合并——默认是覆盖，挂上 Annotated[list[X], operator.add] 就变成追加。
    3. Java 类比：一个贯穿全流程的上下文 DTO；Reducer 像字段级的合并策略（put vs addAll）。
    4. 📖 https://docs.langchain.com/oss/python/langgraph （State/Reducer，需核实锚点）· video-2 P41-43「AgentState 状态详解」、P58-59「工作流的 State 和 Reducer」
  • 引用式字段（*_ref）与 state 瘦身 [R13]
    1. LangGraph Server 每个 superstep 都会把整个 state 快照一次，报告全文/告警原文塞进去 = 每一步都全量重写一遍大文本。
    2. 所以约定：大文本落盘到 runs/incidents/{incident_id}/，state 里只存路径字符串或 id 列表。
    3. Java 类比：大附件传 OSS，数据库里只留一个 URL 字段。
    4. 本模块只负责把这条规矩定死在字段类型和注释里；真正往盘上写文件的是 M5（告警落盘）、M7（证据台账）、M8（报告落盘）。

🟡 第 1 段 · 改造（在本项目真实代码上换状态对象）

python
"""贯穿一次事故全流程的状态对象与预算台账."""

from __future__ import annotations

import operator
from typing import Annotated, Any, TypedDict

from pydantic import BaseModel


class BudgetLedger(BaseModel):
    """一次事故的预算台账：M4 的 guard 在每次 LLM/工具调用前后读写它."""

    tokens_used: int = 0        # 累计 LLM token（prompt+completion），由 guard.charge_tokens() 累加
    token_limit: int = 200_000  # 单次事故的 token 上限，来自 Settings，不硬编码在这里
    tool_calls_used: int = 0    # 累计网关"模板通道"调用次数，由 guard.charge_tool_call() 累加
    tool_calls_limit: int = 40  # 模板通道上限，与 M2 网关侧 per-incident 预算（模板 40）保持一致
    raw_calls_used: int = 0     # 累计 raw 通道调用次数；raw 工具 M7 才接入，M4 恒为 0
    raw_calls_limit: int = 5    # raw 通道上限，与网关侧（raw 5）保持一致，与模板通道分开计
    deadline_ts: float | None = None  # 墙钟截止时间（epoch 秒）；None 表示还没初始化，由 guard.load_ledger() 补上
    budget_exhausted: bool = False    # 任一维度触顶即置 True；report 节点读它，在报告里标注"因预算耗尽提前收口"


class IncidentState(TypedDict, total=False):
    """一次事故从告警进入到报告出口的全流程共享状态.

    硬约定：大文本一律落盘、state 只存 `*_ref` 路径或 id [R13]。
    `total=False` 表示所有字段都可缺省——谁写谁给，读的时候一律用 state.get()。
    """

    # ---- 入口输入 ----
    incident_id: str    # 事故唯一 id；贯穿网关 X-Incident-Id、证据目录名、日志关联。M4 由 run input 给，M5 起由 webhook 生成
    service: str        # 告警直接指向的服务名，是 investigate 的起点（注意：不等于根因服务）。同上
    fingerprint: str    # 告警指纹，30min 去重用。M5 的 webhook 写入（优先取 Alertmanager 自带 fingerprint），M4 恒缺省
    alerts_ref: str     # 原始告警 payload 的落盘路径（不是 payload 本身）。M5 写入，M4 恒缺省

    # ---- 各节点产出 ----
    matched_cases: list[dict]  # 历史相似案例命中列表。M11 的 knowledge_match 节点写入，元素类型届时为 KnowledgeHit
    triage: dict | None        # 分诊结果。M6 的 triage 节点写入，届时类型收紧为 TriageResult（在 M6 定义）
    investigate_rounds: int    # investigate 已跑轮数；条件边靠它判断还能不能回流。由 investigate 节点自己 +1（M4 写）
    evidence: Annotated[list[dict], operator.add]           # 证据条目，追加型。M4 先记 {tool, args}，M7 换成 EV-* 台账条目
    verifier_feedback: Annotated[list[str], operator.add]   # verify 每次打回的意见，回流时注入 investigate 的 prompt（M4 写占位、M9 写真实异议）
    draft_report_ref: str | None  # 报告草稿的落盘路径，不是全文。M7 产出草稿、M8 落最终 report.md
    verify_verdict: dict | None   # 验收结论。M4 先由确定性预检写，M9 补跨家族 LLM 核验，届时类型收紧为 Verdict（在 M9 定义）

    # ---- 降级与预算 ----
    degraded: bool             # 本次链路上是否出现过网关降级；H3 一等信号，任何节点不许吞（M3 起就在写）
    degraded_reason: str | None  # 降级原因原文，来自网关信封同名字段
    budget: dict               # BudgetLedger 的 model_dump()，由 guard 读写（M4 写）

    # ---- 后续模块占位 ----
    approval: dict | None          # 人工审批决定。M12 的 approval 节点写入
    remediation_result: dict | None  # 修复执行结果。M12 的 remediate 节点写入

任务 T4.2 · 条件边/回流 + 调用粒度预算 guard

id：T4.2 ｜ 所属模块：M4 ｜ 优先级：P0

一句话目标：把当前"START → investigate_once → END"的直线，改成带 verify → investigate 回流（≤2 轮）和真正管用的预算 guard 的状态机。

前置知识（≤2 新概念）

  • 条件边 + 回流 + Command(goto)
    1. add_conditional_edges(node, router_fn, {"分支名": "目标节点"})：节点跑完后由 router_fn(state) 返回一个分支名决定下一步去哪。
    2. 路由函数只读不写：它只能返回字符串，改 state 的活必须落在节点的返回值里。
    3. Command(goto="report", update={...})：节点自己决定跳到哪里并顺带更新 state，用于跨越正常边的"紧急收口"。
    4. Java 类比：①③ 是状态机的条件转移；Command(goto=...) 像方法里直接 return nextState 而不是走配置好的转移表。
    5. 📖 https://docs.langchain.com/oss/python/langgraph （conditional edges / Command，需核实锚点）· video-2 P60「节点&路由函数」
  • 调用粒度预算 guard [R8]
    1. token/工具次数/墙钟的检查要落在每一次 LLM 调用和每一次工具调用处，而不是只在节点入口检查一次。
    2. 原因（H6）：M7 之后 investigate 是一个 agent 循环，一个节点内部会连打十几次工具，只在入口拦一次等于整轮不设防。
    3. Java 类比：限流不能只在 Controller 入口拦一次，得在每次下游调用处累计计数。
    4. 📖（自研，无直接文档；网关侧 429 语义见 M2 docs/tool-contract.md [R8]）

🟡 第 1 段 · 改造（在真实 graph.py 上长出条件边）

本项目现在只有 investigate_once 一个节点、两条静态边。直接在真实的 graph.py 上补节点接条件边——不要另开一个脱离本项目的玩具图去"先摸一遍条件边"。

  1. 加 verify 节点：M4 只写 M9 的确定性预检那一半——不调 LLM，纯规则判断"证据够不够"：
    • metrics_result 为空 / degraded=True → Verdict(verdict="fail", objections=["未取到有效指标证据"])；
    • 否则 → pass。
    • 这一半在 M9 会原样保留，M9 只是在它 pass 之后再接一段跨家族 LLM 核验，不会重写它。
  2. 加 report 节点：M4 只让它读 investigate_rounds / verify_verdict / budget.budget_exhausted，结构化打印一行收口日志然后 → END。M8 往这个同一个节点里填真实报告渲染与落盘，不新建文件。
  3. 接边：START → investigate_once → verify，然后
    python
    workflow.add_conditional_edges(
    "verify",
    route_after_verify,
    {"investigate": "investigate_once", "report": "report"},
)
workflow.add_edge("report", END)
  4. route_after_verify(state) -> str 的三条规则：
    1. verdict == "pass" → "report"；
    2. verdict == "fail" 且 investigate_rounds < settings.max_investigate_rounds（=2）→ "investigate"；
    3. verdict == "fail" 且轮数已耗尽 → "report"（兜底出报告，不许无限回流）。
  5. 回流两件事（都必须发生在节点里，不是路由函数里）：
    1. investigate_once 在自己的返回值里 investigate_rounds = state.get("investigate_rounds", 0) + 1；
    2. verify 判 fail 时把 objections 追加进 verifier_feedback；investigate_once 开头读 verifier_feedback，把它拼进 prompt 并声明"增量补证、复用已有 evidence，不要重复取同一份数据"。

🔴 第 2 段 · 自研（从空文件写 guard.py）

签名先定死，再填实现：

python
"""预算与墙钟 guard：在每次 LLM/工具调用处累计并检查，超限即抛，由节点收口."""


class BudgetExhaustedError(Exception):
    """本次事故的 token / 模板通道 / raw 通道 / 墙钟，任一维度触顶."""


def load_ledger(state: IncidentState) -> BudgetLedger:
    """从 state["budget"] 还原台账；首次调用时按 Settings 初始化各上限，
    并把 deadline_ts 补成 now + settings.wall_clock_budget_seconds。"""


def check_budget(ledger: BudgetLedger) -> None:
    """在每次 LLM 调用前、每次网关工具调用前各调一次；
    tokens_used>=token_limit、tool_calls_used>=tool_calls_limit、
    raw_calls_used>=raw_calls_limit、now>=deadline_ts 任一成立就抛 BudgetExhaustedError。"""


def charge_tokens(ledger: BudgetLedger, response: AIMessage) -> BudgetLedger:
    """从 response.usage_metadata["total_tokens"] 累加 tokens_used，返回更新后的台账。
    模型没回 usage_metadata 时按 0 记并留一条日志，不要静默当成没花钱。"""


def charge_tool_call(
    ledger: BudgetLedger, envelope: ApiEnvelope, *, raw: bool = False
) -> BudgetLedger:
    """累加 tool_calls_used（raw=True 时累加 raw_calls_used）；
    并用信封里的 meta.tool_calls_remaining 校准本地计数——两边不一致时以网关为准，
    因为网关那边才是真正会返回 429 的人。"""

节点侧的收口写法（investigate_once 里）：

python
try:
    guard.check_budget(ledger)
    ...  # 真正的 LLM / 工具调用
except (BudgetExhaustedError, BudgetExceededError) as e:
    exhausted = ledger.model_copy(update={"budget_exhausted": True})
    return Command(goto="report", update={"budget": exhausted.model_dump(),
                                          "degraded_reason": str(e)})

    把 budget.deadline_ts 传成一个过去的时间戳发一次请求，看是否在第一次 LLM 调用前就被拦住并跳 report。

关键提示（≤3）

  • guard 检查点必须在"每次调用"处而非节点入口——M7 的 agent 循环一个节点内会连打十几次工具，入口检查形同虚设（H6）。
  • 路由函数只读不写：investigate_rounds 的 +1 放进 route_after_verify 里不会生效，必须落在 investigate_once 的返回值里。
  • 网关的 429（BudgetExceededError）是最后兜底，本地 guard 是提前收口，两个都要有——429 兜不住墙钟超时，本地 guard 也兜不住别的 agent 抢用同一 incident 的预算。

卡住降级路径（30 分钟没思路）

  • 无限回流 / 一次就走 report：打印 investigate_rounds 和 route_after_verify 的返回值，确认返回的字符串是 add_conditional_edges 第三个参数里的分支键（"investigate"），不是节点名。
  • 回流了但 rounds 一直是 0：说明 +1 写在了路由函数里。
  • Command(goto=...) 不生效：确认节点的返回类型标注允许 Command，且目标节点名拼写和 add_node 一致。

真实验收（含异常路径）

bash
cd iris-agent-platform
uv run langgraph dev            # 127.0.0.1:2024

# ① 正常路径：证据取到 → verify pass → report
curl -s -XPOST localhost:2024/runs/wait -H 'Content-Type: application/json' \
  -d '{"assistant_id":"agent",
       "input":{"incident_id":"inc-m4-003","service":"<pm-svc>"}}' \
  | jq '{rounds: .investigate_rounds, verdict: .verify_verdict, budget: .budget}'
# 期望：investigate_rounds=1、verify_verdict.verdict="pass"、budget.tokens_used>0

# ② 回流路径：让证据真的取不到（真实降级，不是伪造 verdict）
docker stop prometheus
curl -s -XPOST localhost:2024/runs/wait -H 'Content-Type: application/json' \
  -d '{"assistant_id":"agent",
       "input":{"incident_id":"inc-m4-004","service":"<pm-svc>"}}' \
  | jq '{rounds: .investigate_rounds, feedback: .verifier_feedback, verdict: .verify_verdict}'
# 期望：investigate_rounds=2 后转 report（不是 3、更不是无限回流）；
#       verifier_feedback 恰好 2 条；verify_verdict.verdict="fail"
docker start prometheus

# ③ 异常路径：墙钟预算已过期
curl -s -XPOST localhost:2024/runs/wait -H 'Content-Type: application/json' \
  -d '{"assistant_id":"agent",
       "input":{"incident_id":"inc-m4-005","service":"<pm-svc>",
                "budget":{"deadline_ts": 1000000000}}}' \
  | jq '{budget: .budget, evidence: .evidence}'
# 期望：budget.budget_exhausted=true；evidence 为空数组（一次工具都没调就收口了）；
#       图正常结束在 report，不是抛栈 500

判定特征：pass 直达 report；真实降级下回流恰 2 轮后收口；deadline 过期时一次调用都不发就跳 report。依赖真实服务：M2 网关、Prometheus、investigate 角色的 LLM。
