任务 T1.1 · 勘察现状 + 可观测三路接线

id：T1.1 ｜ 所属模块：M1 ｜ 优先级：P0

一句话目标：把"prunus-mume 到底长什么样、观测栈能不能查到它"从猜测变成实测记录。

前置知识（≤2 新概念）

  • Micrometer + /actuator/prometheus：Spring 应用暴露指标的标准出口，Prometheus 来抓。Java 类比：你早就用过 Actuator 的 /health，这只是多暴露一个 /actuator/prometheus 文本端点。📖 https://docs.spring.io/spring-boot/reference/actuator/metrics.html （需核实精确锚点）
  • 分布式 trace 的 traceId：一次请求跨多个服务时共享的一个 id，是把 metrics/logs/trace 三路对齐的枢纽。Java 类比：类似你日志里 MDC 放的 requestId，只是它会自动透传到下游 Feign 调用。📖 https://docs.spring.io/spring-boot/reference/actuator/tracing.html （需核实锚点）

🟢 第 1 段 · 复刻（读现有代码 + 跑通探针，先别改）

  • 读什么：prunus-mume 的 pm-common 里 ChaosController（/chaos/register/{name}、/chaos/status、/chaos/isEnabled）源码，看清入参与语义；读各服务 application.yml 的 management/spring.config.import 段。
  • 跑什么：对每个已起的 pm 服务打 curl -s localhost:<port>/chaos/status 和 curl -s localhost:<port>/actuator/prometheus，看它现在到底暴露了什么。
  • 目的：先把"它已经有什么"摸清，避免重复造 M0 里担心的轮子。

🟡 第 2 段 · 改造（缺什么补什么）

  • 若某服务没有 /actuator/prometheus：给它加 micrometer-registry-prometheus 依赖 + management.endpoints.web.exposure.include: prometheus,health（允许改 prunus-mume，改动记入 env-baseline.md）。
  • 若没有 tracing：加 micrometer-tracing + 上报到 Tempo/Zipkin。
  • deploy/prometheus/prometheus.yml 的 scrape target 改成 pm 各服务真实容器名 + /actuator/prometheus 路径。

🔴 第 3 段 · 自研（脱参考写勘察记录）

  • 从空文件写 docs/env-baseline.md：端口表（实测填入）、每个服务的 chaos 清单（/chaos/status 输出）、观测接入现状（有/无 actuator、有/无 tracing）。这份文件是 M2–M12 所有 <占位> 的填充来源。

落笔顺序

  1. 1
    复刻：读 ChaosController + application.yml，curl /chaos/status 与 /actuator/prometheus。
  2. 2
    记录现状到 env-baseline.md（先记事实）。
  3. 3
    改造：补缺的 actuator/tracing，改 prometheus.yml scrape。
  4. 4
    发一次请求看报错：curl 'localhost:9090/api/v1/query?query=up'，看 target 是否 UP。
  5. 5
    自研：补全 env-baseline.md 端口/chaos/观测三张表。

关键提示（≤3）

  • 改 prunus-mume 时每个服务单独改单独验，别六个一起改。
  • 端口从 Nacos 配置读（curl Nacos 配置查询或看 Nacos 控制台），别猜。
  • 三路对齐靠 traceId：先确认一次请求的 traceId 同时出现在 Loki 日志和 Tempo trace 里。

卡住降级路径（30 分钟没思路）

  • 某服务没 /actuator/prometheus：看它 pom.xml 是否缺 micrometer-registry-prometheus；对照 Spring Boot Actuator metrics 文档。
  • 视频：video-4 P42「面试题：模型私有化部署」无关；观测接线无对口视频，以 Spring 官方文档为主。
  • 问 AI：「prunus-mume 的 pm-question 服务，我想让它暴露 /actuator/prometheus，现在 pom 和 application.yml 是这样（贴出），要加哪几行？只给 diff。」

真实 HTTP 验收（含异常路径）

bash
curl -s localhost:<pm-port>/actuator/prometheus | head        # 期望：Prometheus 文本格式指标
curl -s 'localhost:9090/api/v1/query?query=up' | grep -o 'order\|question\|payment'  # 抓到 pm target
# 三路对齐：从一次请求拿 traceId
TID=$(curl -s localhost:<pm-port>/... | ...)   # 取一个 traceId
curl -s "localhost:3100/loki/api/v1/query_range" --data-urlencode "query={container=~\"pm-.*\"} |= \"$TID\""  # Loki 查到
# 异常路径：对未接 actuator 的服务打 /actuator/prometheus → 404，正是"需要改造"的信号

判定特征：/actuator/prometheus 返回文本指标 + Prometheus up 含 pm target + 同 traceId 在 Loki 命中。依赖真实服务：prunus-mume、Prometheus、Loki（+Tempo）。

任务 T1.2 · 设计落到刷题域的故障目录

id：T1.2 ｜ 所属模块：M1 ｜ 优先级：P0

一句话目标：把"要练的 SRE 故障类型"映射到 prunus-mume 的真实服务，产出可注入、可验证的故障目录。

前置知识（≤2 新概念）

  • 故障因果链（causal chain）：一个根因如何一步步传导成表层告警，是评估"诊断对不对"的真值。Java 类比：像一条异常堆栈，但跨服务——根因在底层（如慢查询），顶层才报错（如接口超时）。📖 https://prometheus.io/docs/practices/alerting/ （告警设计，需核实锚点）
  • 注入手段三选一：①prunus-mume 自带 /chaos ②往它代码加钩子（本项目允许）③外部手段（docker/mysql/nacos/tc）。Java 类比：像给某段业务加一个 @Profile("chaos") 的劣化分支，只是可远程开关。

🟢 第 1 段 · 复刻（读参照物）

  • 读什么：① prunus-mume ChaosController + 已注册的 chaos 用法（T1.1 已勘察）；② 一个成熟 SRE Agent 的故障分类，作为"该练哪些类型"的参照——HolmesGPT 或 OpenSRE 的 README/示例故障（📖 https://github.com/robusta-dev/holmesgpt 、https://github.com/swapnildahiphale/OpenSRE ，活跃度需核实）。
  • 目的：先看别人把 SRE 故障分成哪几类，别自己拍脑袋。

🟡 第 2 段 · 改造（映射到 prunus-mume 服务）

  • 把通用故障类型落到 pm 的真实业务点，例如（具体注入点以 T1.1 勘察为准）：
    • 慢查询 → pm-question 题库分页查询（删索引/锁行）
    • 线程池耗尽/下游超时 → pm-payment 支付渠道（/alipay/callback 链路）
    • 缓存故障 → Redis（docker stop redis）
    • 配置变更 → 通过 Nacos 发布改坏某服务配置
    • 实例宕/CrashLoop → docker kill 某 pm 服务
  • 每条标注注入手段（自带/加钩子/外部）与 root_service。

🔴 第 3 段 · 自研（写全一条完整故障）

  • 从空文件写 docs/fault-catalog.md，并把其中一条写到可执行程度：fault_id / fault_class / root_service / 注入手段 / expected_alerts / causal_chain / key_evidence。其余条目先列骨架，随 M3+ 逐步补全。

落笔顺序

  1. 1
    复刻：读 ChaosController + 一个 OSS 的故障分类。
  2. 2

关键提示（≤3）

  • 优先选"有区分度"的故障（同症不同因，如渠道超时 vs 线程池耗尽），这是评估的命根。
  • 注入手段能用自带 /chaos 就别改代码；确需代码内故障（连接池泄漏/GC 压力）才加钩子。
  • 每条必须"可一键 revert 回稳态"，否则不许进目录。

卡住降级路径（30 分钟没思路）

  • 问 AI：「prunus-mume 的 pm-payment 支付链路，我想注入'下游渠道超时'故障，用它自带 /chaos 还是得改代码？给我两种方案的对比，不要直接写实现。」

真实 HTTP 验收（含异常路径）

bash
# 对写全的那条故障：注入 → 看告警 → revert
curl -XPOST "localhost:<pm-port>/chaos/register/<fault_name>" ...   # 或外部手段注入
sleep 90 && curl -s 'localhost:9093/api/v2/alerts' | grep <expected_alert>   # 期望：告警 firing
# revert
curl -XPOST "localhost:<pm-port>/chaos/register/<fault_name>" ...（关闭）
sleep 60 && curl -s 'localhost:9093/api/v2/alerts' | grep <expected_alert>   # 期望：已 resolve/消失
# 异常路径：一条"正常背景变更"不应触发任何告警（阴性对照素材）

判定特征：注入后 ≤2min 出现 expected_alert，revert 后 resolve；阴性变更零告警。依赖真实服务：prunus-mume、Alertmanager、Prometheus。
