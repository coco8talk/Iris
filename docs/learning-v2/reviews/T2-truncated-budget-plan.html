这两个字段目前是无条件常量：truncated 永远 false，budgetRemaining 永远 0。这比"没有这两个字段"更危险——它们向 Agent 传递了确定但虚假的信号（"数据完整" / "预算已耗尽"），而不是显式的"未知"。

1. 前置依赖说明

truncated 目前无法在当前 DTO 形状下有意义地计算。 QueryRangeDTO 里没有 window 字段——调用方直接指定 step（QueryRangeDTO.java:41-44），网关没有做任何"从 window 反推 step"的决策，也就没有"网关主动选择了比原生分辨率更粗的 step"这件事可言。truncated 的语义（本报告背景条款 #3）建立在"网关代码决定 step"这个前提上，而这个前提目前不存在。

因此本方案建立在 T2.1 安全扫描报告 Step A 的改造之上：先把入参从 {query, start, end, step, ...} 换成 {template, service, window, compareBaseline}（WindowQueryDTO），网关代码才有"自己选了什么 step"这个决策点，truncated 才有意义。下面的实现直接假设 WindowQueryDTO 已存在。

2. truncated 怎么算（metrics 场景）

公式

maxPoints = 30 // M2 文档：降采样 ≤30 点
windowSeconds = parse(window) // "30m" → 1800
nativeScrapeIntervalSeconds = MetricsTemplateRegistry.get(template).nativeScrapeIntervalSeconds

stepSeconds = max(nativeScrapeIntervalSeconds, ceil(windowSeconds / maxPoints))
truncated = stepSeconds > nativeScrapeIntervalSeconds

直觉：如果 windowSeconds / maxPoints 算出来比原生 scrape_interval 还细，就没必要降采样，直接用原生分辨率，truncated=false（数据没有被我们主动变粗）。如果算出来比原生分辨率粗，就必须放粗到这个 step 才能凑够 ≤30 点，此时是网关主动牺牲了分辨率，truncated=true。

StepResolver（确定性纯函数，不进 LLM）

public class StepResolver {

    private static final int MAX_POINTS = 30;

    public StepResolution resolve(MetricTemplate template, long windowSeconds) {
        long naive = (long) Math.ceil((double) windowSeconds / MAX_POINTS);
        long stepSeconds = Math.max(template.getNativeScrapeIntervalSeconds(), naive);
        boolean truncated = stepSeconds > template.getNativeScrapeIntervalSeconds();
        return new StepResolution(stepSeconds, truncated);
    }
}

public record StepResolution(long stepSeconds, boolean truncated) {}

nativeScrapeIntervalSeconds 从哪来

不建议实时查 Prometheus /api/v1/targets 元数据（引入额外一次上游调用、增加超时面），改为在 MetricsTemplateRegistry 里按模板静态声明，与"降采样是确定性代码"的原则一致，学习项目里足够：

public record MetricTemplate(
    String promqlTemplate,
    long nativeScrapeIntervalSeconds,   // 例如 15，对齐 prometheus.yml 的 scrape_interval
    int maxPoints
) {}

初始值：若各 target 的 scrape_interval 统一为 Prometheus 默认的 15s，可以先给一个全局默认值，逐个模板按需覆盖；覆盖值应该来自 M1 勘察阶段读到的真实 prometheus.yml，不要拍脑袋。

logs / trace 的 truncated（超前说明，供后续工具复用同一 meta 字段）

这两个工具目前还不存在（见 T2.1 安全扫描报告），但既然复用同一个 ApiEnvelope.Meta.truncated 字段，公式先定下来，避免以后语义漂移：

3. budget_remaining 怎么算

存储：SQLite + 原子 UPDATE...RETURNING

CREATE TABLE IF NOT EXISTS budget_counter (
  incident_id TEXT NOT NULL,
  channel     TEXT NOT NULL CHECK (channel IN ('template','raw')),
  used        INTEGER NOT NULL DEFAULT 0,
  limit_value INTEGER NOT NULL,
  PRIMARY KEY (incident_id, channel)
);

BudgetService

public enum Channel {
    TEMPLATE(40), RAW(5);
    private final int limit;
    Channel(int limit) { this.limit = limit; }
    public int limit() { return limit; }
}

@Service
public class BudgetService {

    private final JdbcTemplate jdbc;

    /** 返回本次调用后的剩余次数；超限抛 BudgetExceededException（映射 429）。 */
    public int consume(String incidentId, Channel channel) {
        // 先保证行存在，SQLite 无原生 UPSERT INCREMENT，分两步但第二步是原子的
        jdbc.update(
            "INSERT INTO budget_counter(incident_id, channel, used, limit_value) " +
            "VALUES (?, ?, 0, ?) " +
            "ON CONFLICT(incident_id, channel) DO NOTHING",
            incidentId, channel.name(), channel.limit());

        Integer used = jdbc.queryForObject(
            "UPDATE budget_counter SET used = used + 1 " +
            "WHERE incident_id = ? AND channel = ? AND used < limit_value " +
            "RETURNING used",
            Integer.class, incidentId, channel.name());

        if (used == null) {
            throw new BudgetExceededException(incidentId, channel);
        }
        return channel.limit() - used;
    }
}
为什么这样能避免并发竞态 UPDATE ... WHERE used < limit_value RETURNING used 是单条 SQL 语句，SQLite 对单条写语句持有的锁保证了"读 used、判断是否超限、+1"这三步在同一行上不可分割地完成——不会出现两个并发请求都读到 used=39、都判断"还没超限"、都各自 +1 变成 41 的情况。queryForObject 在没有行满足 WHERE 条件（即已到达 limit）时返回 null（无匹配行），以此作为超限信号。

429 的异常映射

务必显式声明，不要依赖兜底 T2.1 安全扫描报告已经指出：AuthInterceptor 抛出的 AccessDeniedException/BadRequestException 目前在 GlobalExceptionHandler 里没有专属处理器，会被兜底 handleUnknown 吞成 500 而不是应有的 401/400。新增 BudgetExceededException 时要吸取同样的教训，显式加处理器： 
@ExceptionHandler(BudgetExceededException.class)
public ResponseEntity<ApiEnvelope<?>> handleBudgetExceeded(BudgetExceededException e) {
    return ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS)
            .body(ApiEnvelope.fail("budget exceeded: " + e.getChannel() + " channel", null));
}

挂载位置：Controller 内部调用，而不是 Interceptor

与鉴权不同，budget 消费需要区分"模板通道"还是"raw 通道"，且要在真正命中上游之前尽早失败（省一次 Prometheus 调用）。推荐直接在每个工具 controller 方法的最前面调用 budgetService.consume(...)，而不是塞进通用 HandlerInterceptor——channel 由 controller 自己最清楚（模板 controller 用 Channel.TEMPLATE，raw controller 用 Channel.RAW），没必要在拦截器里反查 URL pattern。

4. 接入 MatricsController

@PostMapping("/query")
public ApiEnvelope<QueryRangeVO> query(
        @Valid @RequestBody WindowQueryDTO req,
        @RequestAttribute("incidentId") String incidentId) {

    long start = System.currentTimeMillis();

    // 1. 预算先扣（省一次可能失败的上游调用）
    int budgetRemaining = budgetService.consume(incidentId, Channel.TEMPLATE);

    // 2. 模板渲染 + step 决策（确定性代码）
    MetricTemplate template = templateRegistry.get(req.getTemplate());
    long windowSeconds = WindowParser.toSeconds(req.getWindow());
    StepResolution step = stepResolver.resolve(template, windowSeconds);
    String promql = templateRegistry.render(req.getTemplate(), req.getService());

    // 3. 调 Prometheus（略，同现有 PrometheusClient 逻辑，query/step 均来自上面两步而非调用方）
    QueryRangeVO data = prometheusClient.queryRange(promql, windowSeconds, step.stepSeconds());

    // 4. 信封：两个字段都来自真实计算
    ApiEnvelope.Meta meta = ApiEnvelope.Meta.builder()
            .elapsedMs(System.currentTimeMillis() - start)
            .truncated(step.truncated())
            .budgetRemaining(budgetRemaining)
            .build();

    return ApiEnvelope.ok(data, meta);
}

incidentId 已经由 AuthInterceptor.java:43 写进 request.setAttribute("incidentId", incidentId)，用 @RequestAttribute 直接取，不用重新解析 header。

6. 验证方式

  • 1StepResolver 单测：构造 (window, maxPoints, nativeScrapeInterval) → 期望 (step, truncated) 的表格用例，纯函数，不需要起 Spring 上下文。
  • 2BudgetService 单测：连续调用 consume 40 次校验递减正确，第 41 次校验抛 BudgetExceededException；多线程并发调用 41 次校验最终 used 恰好停在 40（验证原子性，不多不少）。
  • 3集成验收（对齐 M2 文档 §T2.2 真实 HTTP 验收）：同一 X-Incident-Id 连打 41 次 query_metrics，第 41 次应返回 429；响应体里 budgetRemaining 应逐次递减到 0。
  • 4truncated 观察：用一个 window=24h（触发降采样）和一个 window=5m（不触发）分别打同一个模板，前者 truncated=true，后者 truncated=false。
本方案依赖 T2.1-security-scan.html 中提出的 WindowQueryDTO / MetricsTemplateRegistry 改造先行落地；在此之前，truncated 字段没有自然的计算输入，只能继续保持占位符或返回 unknown 语义。
