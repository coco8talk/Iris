0. 一句话结论

当前 MatricsController 把 Prometheus 原生 query_range 接口（query / start / end / step / timeout / limit / lookbackDelta / stats）几乎逐字段透传给外部调用方。 这意味着"降采样 step 由网关代码从 window 反推""service 走白名单/CMDB 校验""raw 逃生通道单独收口"这三条设计红线目前一条都没有落地。 对照 M2 文档的三段式（🟢复刻 → 🟡改造 → 🔴自研），现状仍停留在🟢第 1 段"复刻"——"先直接返回上游原始 JSON"的阶段特征——尚未进入 🟡改造段（模板端点、降采样）,更谈不上 🔴自研段（横切面）。 已完成的只有骨架层：鉴权拦截器、全局异常分层、ApiEnvelope 信封结构。

2. 注入防护判定

M2 文档设计里"模板通道"与"raw 通道"是两条应该分别收口的路径：

路径预期约束当前 MatricsController.query() 现状
模板通道 query 由 MetricsTemplateRegistry 从 {template, service} 代码拼出，调用方不接触 PromQL 原文，service 参数化嵌入而非字符串拼接 不存在——没有 template/service 字段，没有模板拼装代码
raw 通道 调用方可裸传 PromQL，但必须先过 RawQueryValidator：长度 ≤500、强制含 label matcher、违规 403、独立预算 5 次/incident 不存在——没有 RawController/RawQueryValidator，没有长度/selector 校验，没有独立预算
判定结论 两条路径目前都不存在。现状等价于一个没有任何限制的裸 raw 通道——调用方通过 @Valid @RequestBody QueryRangeDTO 直接控制 query 字段（任意 PromQL）、step（分辨率）、limit（返回序列数上限，@PositiveOrZero 只挡负数，0 表示不限制）、lookbackDelta 等全部原生参数。 但对外接口路径 POST /matrics/query、Swagger 文档描述"封装 Prometheus query_range 接口的指标查询工具"、以及 @Valid 校验注解带来的观感，都在暗示这是一个受控的"模板工具"——这是最容易被忽视的落差：看起来安全（有校验注解、有信封包装），实际上和裸调 Prometheus 没有区别。

具体可被利用的点

  • 任意 PromQL：query 字段（QueryRangeDTO.java:29）只有 @NotBlank，调用方可传高基数正则如 {__name__=~".+"} 造成 Prometheus 侧 cardinality/regex 扫描压力，或跨 service/跨租户查询本不该由该 incident 看到的指标。
  • 分辨率失控：step 字段（QueryRangeDTO.java:41-44）由调用方直传，可传极小值（如 1s）配合大窗口制造超大响应体，与设计结论 #2 的"step 必须由网关反推、不能比原生 scrape_interval 更细"完全相反。
  • 返回量不设上限：limit 字段（QueryRangeDTO.java:50-52）只挡负数，0=不限制是 Prometheus 原生语义，网关未覆盖成安全默认值。
  • 无调用次数上限：因为 BudgetService 不存在，以上每一种滥用都可以被无限次重复。

3. 附带发现：BeanUtil.beanToMap 的静默失效风险

MatricsController.java:74-78：

Map<String, Object> queryRangeMap = BeanUtil.beanToMap(
        queryRangeDTO,
        new HashMap<>(),
        true,
        true);

已用 javap 反编译 hutool-all-5.8.47.jar 里的 BeanUtil 确认，这里调用的重载是：

public static Map<String, Object> beanToMap(Object, Map<String, Object>, boolean, boolean)

对应签名 (bean, targetMap, isIgnoreNullValue, isIgnoreError)——不带任何命名策略（NamingCase）或 CopyOptions 参数。也就是说 map 的 key 就是 Java 字段名本身（驼峰），不会转成 Prometheus 官方接口要求的 snake_case。

受影响字段：lookbackDelta（应为 lookback_delta）。查询参数会以 lookbackDelta=5m 的形式拼进 URL；Prometheus HTTP API 对未识别的 query 参数是静默忽略而非报错，所以调用方即使认真传了 lookbackDelta，这个值也不会生效，且不会有任何错误提示——这是一个"看起来传了参数，实际上完全没用"的静默失效点。

5. 实现方案（按 复刻 → 改造 → 自研 顺序）

下面按 M2 文档 T2.1/T2.2 的三段式给出落地步骤。🟢复刻段（curl 裸打 Prometheus + 当前 /matrics/query 透传骨架）已完成，方案从 🟡改造段开始。

🟡 Step A — 模板通道：把 query_metrics 从"裸透传"改造成"模板端点"

  1. 新增 WindowQueryDTO（对外暴露的唯一入参形状）：

    端点改为 POST /api/v1/tools/query_metrics（对齐文档路径，与当前 /matrics/query 不一致，属于同一批要修的命名缺口）。
  2. 新增 MetricsTemplateRegistry：
    • 职责：维护 Map<String, MetricTemplate>，MetricTemplate{promqlTemplate, nativeScrapeIntervalSeconds, maxPoints}。
    • render(templateKey, service)：service 先过白名单正则 + CMDB 校验（Step A.3），再用占位符替换生成最终 PromQL——调用方全程不接触 PromQL 原文。
    • 未知 templateKey → 400（而不是把它当 PromQL 执行）。
  3. 新增 ServiceRegistry（先给静态白名单占位，T2.2 段2 再接 CMDB/Nacos 动态解析）：isKnown(String service)，未知 service → 400。
  4. 新增 StepResolver（确定性纯函数，算法与 truncated 判定见任务 3 报告）。
  5. PrometheusClient：把当前 controller 里直接拼 URL 的逻辑收敛进这一层；继续使用 UriComponentsBuilder.queryParam（本身会做 URL 编码，不是拼接注入的风险点——真正风险是"值"不受控，而不是"拼接方式"），但传入的 query 永远来自 MetricsTemplateRegistry.render() 的产物，不再是调用方原始输入。

public String render(String templateKey, String service, String window) {
    MetricTemplate t = registry.get(templateKey);
    if (t == null) throw new UnknownTemplateException(templateKey);
    return t.promqlTemplate()
            .replace("{service}", service)   // service 已在 ServiceRegistry 白名单校验通过
            .replace("{window}", window);    // window 已被 @Pattern 钳制为 \d+[smhd]
}

🔴 Step C — 现有 /matrics/query 端点的收编

不能让"看起来像模板工具的路径"继续暴露"完全裸露的参数"。二选一：
