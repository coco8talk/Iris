## 任务 T4.1 · 状态对象 + checkpointer 记忆

**id**：T4.1 ｜ **所属模块**：M4 ｜ **优先级**：P0

**一句话目标**：把 M3 的临时 state 升级为正式 `IncidentState`，并接上 SqliteSaver 实现断点续跑。

**前置知识（≤2 新概念）**
- **IncidentState（TypedDict）+ Reducer**：整条事故流程共享的状态字典；Reducer 决定同一字段多次写入如何合并（如 append）。*Java 类比*：一个贯穿全流程的上下文 DTO，Reducer 像字段级的合并策略（覆盖 vs 累加）。📖 https://docs.langchain.com/oss/python/langgraph （State/Reducer，需核实锚点）· video-2 P41-43「AgentState 状态详解」
- **checkpointer（SqliteSaver）**：每步把 state 存盘，`thread_id` 标识一次会话，可从任意节点恢复。*Java 类比*：像把 HttpSession/工作流实例状态持久化到库，重启后按 id 捞回来接着跑。📖 https://docs.langchain.com/oss/python/langgraph （persistence/checkpointer，需核实锚点）· video-2 P44-47「记忆存储·短期·Postgres」

### 🟢 第 1 段 · 复刻
- **读什么**：LangGraph 官方 persistence 示例里 `StateGraph(...).compile(checkpointer=SqliteSaver(...))` + `config={"configurable":{"thread_id":...}}` 的最小用法。
- **跑什么**：照样例跑一个两节点图，`thread_id` 固定，验证第二次调用能读到第一次的 state。

### 🟡 第 2 段 · 改造
- 把 state 换成 `IncidentState`（incident_id/alerts_ref/triage/investigate_rounds/draft_report_ref/budget/...）；`thread_id = incident_id`；用 `AsyncSqliteSaver`（FastAPI 异步路径）。

### 🔴 第 3 段 · 自研
- **从空文件**写子模型：`TriageResult / RcaReport / Verdict / BudgetLedger`；并落实**大文本落盘、state 只存引用** [R13]——报告 md、原始告警落 `runs/incidents/{id}/`，state 存路径/ids。

**落笔顺序**
1. 复刻官方 checkpointer 样例，验证断点续跑。
2. 改造 state 为 IncidentState、thread_id=incident_id。
3. 发一次请求：跑到一半 kill 进程。
4. 填逻辑：重启后用同 incident_id 恢复，确认从上次节点继续。
5. 自研子模型 + 大文本落盘。

**关键提示（≤3）**
- `thread_id` 必须等于 incident_id，否则记忆对不上事故。
- 别把整份报告 md 塞进 state——只存路径，否则每步 checkpoint 全量序列化会膨胀。
- 子模型用 Pydantic，判分字段（root_service/root_cause）后面要确定性比对，别让 LLM 乱改。

**卡住降级路径（30 分钟没思路）**
- 恢复不了：确认两次调用 `thread_id` 一致、checkpointer 是持久化版（不是 InMemory）。
- 视频：video-2 P45-46「短期记忆案例·Postgres 短期存储」对口讲解。
- 问 AI：「LangGraph 用 AsyncSqliteSaver，我 kill 进程重启后 `ainvoke` 同一 thread_id 却从头跑，我的 compile 和 config 这样写（贴出），哪里错了？」

**真实 HTTP 验收（含异常路径）**
```bash
curl -XPOST localhost:8000/webhook/... -d @alert-fixture.json   # 启动一次事故图
# 在图跑到 investigate 时 kill uvicorn，重启
# 用同 incident_id 触发恢复
sqlite3 runs/checkpoints.db "select count(*) from checkpoints where thread_id='inc-...';"  # >0
# 异常路径：用不同 thread_id 恢复 → 从头开始（证明记忆按 incident 隔离）
```
判定特征：checkpoints.db 有该 thread 的多步记录；kill-重启后同 incident 续跑、异 incident 从头。依赖真实服务：网关（图内工具会真实调用）。

**完成判定**

## 任务 T4.2 · 条件边/回流 + 调用粒度预算 guard

**id**：T4.2 ｜ **所属模块**：M4 ｜ **优先级**：P0

**一句话目标**：接上 verify→investigate 回流（≤2 轮）和真正管用的预算 guard。

**前置知识（≤2 新概念）**
- **条件边 + 回流 + Command(goto)**：节点后按条件决定去哪；verify 失败可回 investigate 再查一轮。*Java 类比*：状态机的条件转移；`Command(goto="report")` 像显式 `return nextState`。📖 https://docs.langchain.com/oss/python/langgraph （conditional edges，需核实锚点）· video-2 P60「节点&路由函数」
- **调用粒度预算 guard**：token/墙钟上限的检查要落在**每次 LLM/工具调用**处，而非只在节点入口。*Java 类比*：像限流不能只在接口入口拦一次，得在每次下游调用处累计计数。📖（自研，无直接文档；参考网关 429 语义 [R8]）

### 🟢 第 1 段 · 复刻
- **读什么**：LangGraph 官方条件边示例 `add_conditional_edges(node, router_fn, {...})`。
- **跑什么**：照样例跑一个"根据 state 值走不同分支"的最小图。

### 🟡 第 2 段 · 改造
- 实现真实条件边：`verify`→pass→`report`；fail 且 `investigate_rounds<2`→`investigate`（rounds+1、注入 feedback）；fail 耗尽→`report`。

### 🔴 第 3 段 · 自研
- **从空文件**写 `guard.py`：在 GatewayClient 回调/工具封装内累计 token，并在 agent 循环内检查上限 [R8]；超限用 `Command(goto="report")` 显式路由 [R14]；节点内捕获 `BudgetExceededError` 置 `budget_exhausted=True`。

**落笔顺序**
1. 复刻官方条件边样例。
2. 改造出 verify→investigate 回流，先用假 verdict 驱动。
3. 发请求：强制 verify 返回 fail，看是否回流 2 次后转 report。
4. 自研 guard：把 deadline 设为过去，看是否直接跳 report。
5. 验证 rounds 计数与 guard 都对。

**关键提示（≤3）**
- 回流时要给 investigate 注入 verifier_feedback，并声明"增量补证、复用已有 evidence_id"。
- guard 检查点要在"每次调用"而非节点入口，否则单个 investigate 节点内多轮循环会冲破上限（H6）。
- 网关的 429 是硬兜底，但内层 agent 循环也要能感知预算。

**卡住降级路径（30 分钟没思路）**
- 回流不生效：打印 `investigate_rounds` 与 router_fn 的返回值，看分支键对不对。
- 视频：video-2 P58-59「工作流的 State 和 Reducer」帮理解回流时状态怎么合并。
- 问 AI：「LangGraph 条件边，我想 verify fail 时回 investigate 最多 2 次，我的 router_fn 这样写（贴出），为什么它无限回流/一次就走 report？」

**真实 HTTP 验收（含异常路径）**
```bash
# 用可控 fixture 强制 verify=fail：观察日志/state
curl -XPOST localhost:8000/webhook/... -d @alert-fixture.json
sqlite3 runs/checkpoints.db "... investigate_rounds ..."   # 期望：回流到 2 后走 report
# 异常路径：把 deadline_ts 设为过去 → guard 让图直达 report（不再 investigate）
```
判定特征：verify fail 回流恰 2 轮后 report；deadline 过期时 guard 跳过 investigate。依赖真实服务：网关、LLM。

**完成判定**
- [ ] 官方条件边样例复现（复刻段）
- [ ] verify→investigate 回流 ≤2 轮，rounds 计数正确
- [ ] guard 在调用粒度检查，deadline 过期能跳 report
- [ ] 超预算用 Command(goto="report") 显式收口
- [ ] `budget_exhausted` 能被 report 节点读到并标注
