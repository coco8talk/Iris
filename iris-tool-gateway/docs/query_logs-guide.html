query_logs 模块设计讲解与实现计划

主题：Loki 日志查询工具（pattern 聚合 + traceId 提取）的设计原理与落地步骤 · 代码库：iris-tool-gateway · 文档生成日期：2026-08-02

前半部分讲原理（全程类比你已经理解的 query_metrics / Prometheus），后半部分是可勾选的实现步骤。

先说明一处偏差：这份文档里所有"现状代码"的引用都基于我刚重新读过的仓库当前源码，不是照抄 UNIMPLEMENTED_FEATURES_REPORT.html（那份报告生成于 2026-08-01，之后仓库已经继续往前走了）。举个例子，那份报告里说 ToolCallsExceededException 没有映射成 429、raw 通道完全不存在——这两点现在都已经落地了（RedisService.consume_raw_tool_calls、GlobalExceptionHandler.handleToolCallsExceeded 均已存在）。后面讲 query_metrics 现有实现时，以我现在读到的代码为准。

1讲解篇

类比Loki 是什么：把它当成"日志界的 Prometheus"

你已经理解 Prometheus 是什么了，所以最快的理解路径是先看两者的骨架有多像，再看差在哪。

生活类比 Prometheus 像工厂里给每台机器装的数字仪表盘：每隔几秒记一次读数（温度、转速），擅长回答"这个数值现在/过去是多少、趋势如何"。Loki 更像车间的值班日志本：操作工每次动作、每次报警都往本子上写一行文字（"10:03 A 线急停""10:05 王师傅按复位"），擅长回答"当时具体发生了什么事、谁干的、报了什么错"。

骨架相同的部分

  • 都按 label（标签） 分组存储数据——Prometheus 用 {application="pm-auth"}，Loki 用 {service="order-svc"}。
  • 都有配套的查询语言——PromQL 对应 LogQL，语法长得非常像（都是"花括号 label 选择器 + 后续处理"的结构）。
  • 都通过 HTTP query_range 接口对外提供"查一段时间窗口"的能力，请求参数（query/start/end/step）几乎一一对应。

本质不同的部分

  • Prometheus 存的是数字（一个时间点对应一个浮点数），Loki 存的是原始文本行（一个时间点对应一整行日志）。
  • 这个差异直接决定了网关侧的处理方式必须不同：query_metrics 可以把 Prometheus 的原始 JSON 直接透传给 agent（反正只是几十个数字点）；query_logs 绝不能把 Loki 返回的几千行原始文本直接透传——这就是为什么规格要求"pattern 聚合"，后面 专门讲。

正因为两者骨架相似，query_logs 的整体代码结构（Controller 初始化带超时的 RestClient、Controller 里先消费预算再请求上游、上游异常复用 GlobalExceptionHandler 的降级分支）几乎可以照抄 MetricsController 的模子，不需要发明新模式。

概念可观测性三兄弟：log / metric / trace 怎么分工

这三者是可观测性领域里最基础的分类，各自回答不同的问题，通过 service 名 和 traceId 横向关联在一起。

类型数据形态回答的问题本项目对应工具
metric（指标）数字随时间变化的曲线"现在/过去这个数值是多少、正常吗"query_metrics（已实现）
log（日志）一行行带时间戳的原始文本"当时具体发生了什么事、报了什么错"query_logs（本文档主题）
trace（调用链）一次请求跨多个服务的完整路径树"这次请求具体走了哪些服务、卡在哪一跳"query_trace（未实现，见报告）
典型排障流程（investigate agent 的视角） 先用 query_metrics 发现异常（某服务 QPS 掉了 / 错误率升了）→ 定位到具体 service 和时间窗口 → 用 query_logs 查这段窗口的错误日志内容，聚合后顺手拿到几个 traceId → 拿着 traceId 去 query_trace 查完整调用链，看请求具体卡在哪一跳。三个工具串成一条排障链路，query_logs 是承上启下的中间一环。

术语辨析traceId 和 spanId 到底有什么区别

生活类比：快递物流 一次网购下单是一个 trace（从下单到签收的完整旅程），trace_id 就是这张快递单号——全程唯一，扫哪个物流网点都能查到同一单号。这趟旅程被拆成"仓库→分拣中心""分拣中心→你所在城市""网点→你家"几段运输区间，每一段就是一个 span，每段有自己的运单流水号 span_id；段与段之间通过"上一段是谁"（parent_id）首尾相连，拼成完整链路。
trace_id
标识"这一整趟请求"，同一次请求经过的所有 span 共享同一个 trace_id。这是日志和调用链之间的"外键"。
span_id
标识"这一小段工作"（比如一次 RPC 调用、一次数据库查询）。一个 trace 由多个 span 组成，span 间靠 parent_id 建立父子层级。

回到 query_logs 的设计目的：日志行里经常会打印 trace_id=xxx（业务代码打点写的），但很少会打印 span_id（那是链路追踪 SDK 内部用的，日志里意义不大）。所以本模块只提取 traceId，不提取 spanId——提取出的 traceId 是给下一步 query_trace 用的钥匙。

类比pattern 聚合具体是在做什么操作

生活类比：超市小票 一天几千张收银小票，你不会一张张去看，而是按"商品名"把小票分组，统计"每种商品卖了多少张、总共卖了多少件"。日志的 pattern 聚合同理：把"骨架相同、只有变量部分（IP、时间戳、订单号）不同"的日志行归成一组，最终报出"这个模式一共出现了几次 + 给一条原文示例"，而不是把几千行原始日志照单全收甩给 agent。

举个具体例子：假如 1 分钟内产生了 3000 条长得像下面这样的日志（只有 IP 和端口不同）：

2026-08-02 10:00:01 ERROR Connection timeout to db-node-1:5432
2026-08-02 10:00:02 ERROR Connection timeout to db-node-2:5432
2026-08-02 10:00:03 ERROR Connection timeout to db-node-3:5432
... （还有 2997 条，骨架完全一样）

聚合后应该变成 1 条记录：{pattern: "ERROR Connection timeout to db-node-N:5432", count: 3000, sampleLine: "...db-node-1:5432"}。这样 agent 一眼就能看出"这一分钟主要在报数据库连接超时"，而不用自己去数几千行文本。

两个不做的事情：不做语义分析（不判断这条日志"是不是异常"，纯粹按文本骨架分组）；不做全量存储（聚合是内存里的一次性计算，不落库、不建索引）。

概念LogQL 基础：只需要认识两个积木

query_logs 网关内部会拼 LogQL 发给 Loki，但 agent 调用方不需要写 LogQL——就像 query_metrics 的调用方只传 templateKey，不用写 PromQL 一样。你只需要认识拼出来的 LogQL 长什么样。

积木一：log stream selector（花括号部分）

必须存在，作用是"先圈定范围"，等价于 PromQL 的 label 选择器：

{service="order-svc"}

支持 = / != / =~（正则匹配）/ !~（正则不匹配）四种操作符，本模块只用得到最简单的 =。

积木二：line filter（管道后面的部分，可选）

跟在 selector 后面用 | 拼接，官方文档原话是"do a distributed grep over the aggregated logs"——本质就是分布式 grep：

{service="order-svc"} |= "error"          # 包含子串 "error"
{service="order-svc"} |~ "timeout|refused" # 匹配正则

本模块设计里，DTO 的 pattern 字段（调用方传入的关键字/正则）会被拼成 |~ "..." 这种 line filter，追加在 selector 后面。

这就是全部要知道的 LogQL 语法——聚合函数、结构化日志解析器（| json / | logfmt）这些进阶用法本模块暂时用不到，属于 raw 逃生通道用户直接手写查询时才需要精通的范畴，不在本文档展开。

对照代码DTO / VO：直接读 metrics 包的现成代码

生活类比：快递面单 DTO 像你填的寄件面单（告诉快递员：寄给谁、寄到哪、多重）——装的是"调用方传进来的东西"。VO 像快递公司返给你的运单详情（经过了哪些网点、当前状态）——装的是"网关要返回出去的东西"。方向相反，但都只是"数据的搬运容器"，本身没有业务逻辑。

先看现成的：WindowQueryDTO（query_metrics 的入参）

真实文件在 metrics/model/dto/WindowQueryDTO.java，关键字段：

字段类型校验注解作用
serviceString@NotBlank @Pattern(^[a-zA-Z0-9._-]+$)目标服务名，白名单字符防注入
windowint@Positive @Max(86400)查询窗口（秒），上限 24 小时
endOffsetSecondsLong@PositiveOrZero把窗口向过去平移，不强制 end=now
templateKey / queryString@AssertTrue 二选一模板通道 / raw 逃生通道，互斥

推演出来的：QueryLogsDTO（query_logs 的入参，建议设计）

service、window、endOffsetSeconds 三个字段和 WindowQueryDTO 语义完全一致，直接照抄校验注解；额外只需要一个新字段 pattern（对应 LogQL 的 line filter，可选）：

@NotBlank @Pattern(regexp = "^[a-zA-Z0-9._-]+$")
private String service;          // 与 WindowQueryDTO 完全同构

@Positive @Max(86400)
private int window;              // 与 WindowQueryDTO 完全同构

@PositiveOrZero
private Long endOffsetSeconds;   // 与 WindowQueryDTO 完全同构

@Size(max = 200)
private String pattern;          // 新增：可选的日志内容过滤关键字/正则

VO 的设计分歧点（重要）

query_metrics 的 QueryRangeVO 是 Prometheus 原始响应结构的直接映射（网关不加工，透传给 agent）。query_logs 不能这样做——原因见前面的 pattern 聚合 小节：Loki 原始响应可能是几千行文本，直接透传会打爆 agent 上下文。所以 QueryLogsVO 装的不是"Loki 原始结构"，而是"网关聚合完之后的结果"，字段设计见 实现计划篇。

总览总体设计一览

新增包 com.silas.iris.toolgateway.logs，结构对齐 metrics 包：

com.silas.iris.toolgateway.logs
├── controller/LogsController.java        POST /logs/query
├── model/dto/QueryLogsDTO.java           入参

代码QueryLogsDTO

package com.silas.iris.toolgateway.logs.model.dto;

import com.silas.iris.toolgateway.logs.constant.LogsQueryConstants;
import io.swagger.v3.oas.annotations.media.Schema;
import jakarta.validation.constraints.*;
import lombok.Data;

@Data
public class QueryLogsDTO {

    @NotBlank
    @Size(max = 64)
    @Pattern(regexp = "^[a-zA-Z0-9._-]+$", message = "service 只允许字母数字. _ -")
    @Schema(description = "服务名，对应 Loki 日志的 service label",
            example = "order-svc", requiredMode = Schema.RequiredMode.REQUIRED)
    private String service;

    @Positive(message = "window 必须大于 0")
    @Max(value = LogsQueryConstants.MAX_WINDOW_SECONDS, message = "window 不能大于 24 小时")
    @Schema(description = "时间窗口(秒)", example = "300", requiredMode = Schema.RequiredMode.REQUIRED)
    private int window;

    @PositiveOrZero(message = "endOffsetSeconds 不能为负")
    @Schema(description = "查询结束时间相对当前时刻的回溯偏移量(秒)，语义与 query_metrics 同名字段一致",
            example = "0")
    private Long endOffsetSeconds;

    @Size(max = 200, message = "pattern 长度不能超过 200")
    @Schema(description = "可选的日志内容过滤关键字/正则，转换为 LogQL line filter；为空则不过滤",
            example = "error")
    private String pattern;
}

和 WindowQueryDTO 不同：这里不需要"模板/raw 二选一"的 @AssertTrue 校验，因为 query_logs 现阶段只有一条通道，没有 raw 逃生通道的需求（除非你后续想加）。

代码QueryLogsVO

package com.silas.iris.toolgateway.logs.model.vo;

import io.swagger.v3.oas.annotations.media.Schema;
import lombok.*;
import java.util.List;

@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
@Schema(description = "日志 pattern 聚合结果")
public class QueryLogsVO {

    @Schema(description = "本次窗口内 Loki 实际返回的原始日志行数（聚合前）")
    private int totalLines;

    @Schema(description = "聚合后的日志模式列表，按 count 降序")
    private List<PatternGroup> patterns;

    @Schema(description = "本次窗口内提取到的全部去重 traceId，可直接作为 query_trace 的入参")
    private List<String> distinctTraceIds;

    @Data
    @Builder
    @NoArgsConstructor
    @AllArgsConstructor
    @Schema(description = "单个日志模式的聚合结果")
    public static class PatternGroup {

        @Schema(description = "归一化后的日志模式骨架（数字/uuid/ip 等变量部分已替换为占位符）")
        private String pattern;

        @Schema(description = "该模式在窗口内出现的次数")
        private long count;

        @Schema(description = "该模式的一条原始日志示例")
        private String sampleLine;

        @Schema(description = "该模式下提取到的 traceId（去重）")
        private List<String> traceIds;
    }
}

这里 totalLines（聚合前行数）和聚合后 patterns.size()（模式组数）的差值，就是"这次查询帮你省了多少行文本"的直观体现——比如 3000 行日志聚合成 4 个模式，agent 一眼就能感知到聚合的价值。

代码LogsController 骨架

@Slf4j
@RestController
@RequestMapping("/logs")
@Validated
@Tag(name = "Logs 查询", description = "封装 Loki query_range，返回 pattern 聚合 + traceId 提取结果")
public class LogsController {

    private final RedisService redisService;
    @Value("${iris.loki.base-url}") private String lokiBaseUrl;
    @Value("${iris.loki.connect-timeout-ms:3000}") private int connectTimeoutMs;
    @Value("${iris.loki.read-timeout-ms:10000}") private int readTimeoutMs;
    private RestClient lokiClient;

    public LogsController(RedisService redisService) {
        this.redisService = redisService;
    }

    @PostConstruct
    void initLokiClient() {
        // 与 MetricsController#initPrometheusClient 同构：显式设超时，
        // 否则 Loki 挂起时线程会无限期占用，degraded 分支永远等不到异常抛出
        SimpleClientHttpRequestFactory requestFactory = new SimpleClientHttpRequestFactory();
        requestFactory.setConnectTimeout(connectTimeoutMs);
        requestFactory.setReadTimeout(readTimeoutMs);
        this.lokiClient = RestClient.builder()
                .baseUrl(lokiBaseUrl)
                .requestFactory(requestFactory)
                .build();
    }

    @PostMapping("/query")
    public ApiEnvelope<QueryLogsVO> query(
            @Valid @RequestBody QueryLogsDTO dto,
            @RequestAttribute(HeaderConstants.INCIDENT_ID_ATTR) String incidentId) {

        long startTask = System.currentTimeMillis();

        // 1. 限流：见下方"复用现有横切机制"一节，这里有一个需要你拍板的设计决策
        Long remaining = redisService.consume_tool_calls(incidentId);

        // 2. 拼 LogQL，推算时间范围（resolveTimeRange 与 MetricsController 完全同构，直接照抄）
        String logQL = LogQlBuilder.build(dto.getService(), dto.getPattern());
        TimeRange range = resolveTimeRange(dto.getWindow(), dto.getEndOffsetSeconds());

        // 3. 请求 Loki，拿到原始逐行日志（内部结构，不对外返回）
        LokiQueryRangeVO raw = fetchQueryRange(logQL, range);

        // 4. 网关内聚合：pattern 分组 + traceId 提取，不透传原始逐行日志
        QueryLogsVO data = LogPatternAggregator.aggregate(raw);

        return ApiEnvelope.ok(data, buildMeta(startTask, remaining, data));
    }

    // fetchQueryRange() 用 lokiClient.get().uri(...).retrieve().body(LokiQueryRangeVO.class)，
    // 与 MetricsController#fetchQueryRange 同构；buildMeta() 额外根据 data 是否被截断设置 truncated
}

代码LogQlBuilder

package com.silas.iris.toolgateway.logs.utils;

import cn.hutool.core.util.StrUtil;

public final class LogQlBuilder {
    private LogQlBuilder() {}

    public static String build(String service, String pattern) {
        String selector = "{service=\"" + service + "\"}";
        if (StrUtil.isBlank(pattern)) {
            return selector;
        }
        // pattern 来自调用方输入，拼进 line filter 前必须转义双引号；
        // 长度已由 DTO 的 @Size(max=200) 兜底，避免恶意超长正则拖垮 Loki（ReDoS 风险）
        String escaped = pattern.replace("\"", "\\\"");
        return selector + " |~ \"" + escaped + "\"";
    }
}

这个类和 MetricsTemplateUtil.render() 是同一个角色：调用方不接触查询语言原文，只传结构化参数，网关内部负责拼装。

代码pattern 聚合 + traceId 提取

package com.silas.iris.toolgateway.logs.constant;

import java.util.regex.Pattern;

public final class LogsQueryConstants {
    private LogsQueryConstants() {}

    public static final int MAX_WINDOW_SECONDS = 24 * 60 * 60;
    public static final String QUERY_RANGE_PATH = "/loki/api/v1/query_range";
    public static final int MAX_RAW_LINES = 5000;      // 单次向 Loki 拉取的行数上限
    public static final int MAX_PATTERN_GROUPS = 30;   // 返回给 agent 的模式组数上限

    // 匹配 trace_id=xxx / traceId:"xxx" / trace-id: xxx 等常见写法
    public static final Pattern TRACE_ID_PATTERN =
            Pattern.compile("(?i)trace[_-]?id[\"']?\\s*[:=]\\s*[\"']?([a-f0-9]{16,32})");
}
package com.silas.iris.toolgateway.logs.utils;

import java.util.regex.Matcher;
import java.util.Optional;
import static com.silas.iris.toolgateway.logs.constant.LogsQueryConstants.TRACE_ID_PATTERN;

public final class TraceIdExtractor {
    private TraceIdExtractor() {}

    public static Optional<String> extract(String line) {
        Matcher matcher = TRACE_ID_PATTERN.matcher(line);
        return matcher.find() ? Optional.of(matcher.group(1)) : Optional.empty();
    }
}

LogPatternAggregator.aggregate() 的实现思路（伪代码，实际实现时按此展开）：

1. 展开 raw.data.result 里每个 stream 的 values 列表，拿到全部 [纳秒时间戳, 原始行文本]
2. 对每一行：
   a. 用 TraceIdExtractor.extract(line) 尝试提取 traceId
   b. 做骨架归一化：把数字串替换成 "N"、uuid 替换成 "<uuid>"、IP 替换成 "<ip>"，
      得到这一行的"归一化骨架"作为分组 key
3. 按归一化骨架分组计数（Map<骨架, 计数+首个原文+traceId 集合>）
4. 按 count 降序排序，超过 MAX_PATTERN_GROUPS 时只保留前 N 组，
   并把"是否发生了截断"这个信号透传给 ApiEnvelope.Meta.truncated
5. 汇总所有分组的 traceId 集合，去重后作为 distinctTraceIds
这一步的第 4 条是一个相对 query_metrics 现状的真实改进点：MetricsController#buildMeta() 目前把 truncated 硬编码成 false（见前文 提到的透传设计），而 query_logs 从设计之初就能算出真实的截断信号，不需要走这个弯路。

需要你拍板复用现有横切机制（含一处预算共享问题）

  • 鉴权：AuthInterceptor 用 addPathPatterns("/**") 全局注册，/logs/** 自动被覆盖，无需任何改动。
  • 上游降级：GlobalExceptionHandler 已有 ResourceAccessException / HttpServerErrorException.ServiceUnavailable → 200 degraded 的映射，Loki 超时/不可达会自动走这条路径，前提是 initLokiClient() 和 MetricsController 一样显式设置了 connect/read timeout。
  • service 校验：等 query_cmdb 落地后，复用已经注册好 400 映射的 UnknownServiceException，不需要新建异常类。
需要你决定的一件事：预算是否共享 RedisService.consume_tool_calls(incidentId) 用的 Redis key 是 consume_tool_calls:template:{incident_id}——如果 query_logs 直接调用这个方法，它会和 query_metrics 共用同一份 30 次/24h 的预算，也就是说一个 incident 下两个工具加起来一共只有 30 次调用机会，不是各自 30 次。

两个选项：
A）共享预算（推荐，改动最小）：语义是"模板通道总预算 30 次"，不区分具体是 metrics 还是 logs，直接复用现有方法，不用改 RedisService。
B）独立预算：仿照 consume_raw_tool_calls 的做法，在 RedisService 里新增 consume_logs_tool_calls(incidentId)，用新 key consume_tool_calls:logs:{incident_id} + 独立限额，两者互不挤占。
