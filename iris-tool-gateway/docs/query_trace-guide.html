query_trace 模块设计讲解与实现计划

主题：Tempo/Zipkin 调用链查询工具（span 树 + 深度精简）的设计原理与落地步骤 · 代码库：iris-tool-gateway · 文档生成日期：2026-08-02

前半部分讲原理（全程类比你已经理解的 query_logs / traceId），后半部分是可勾选的实现步骤。

两处说明：① query_trace 目前仍是未实现状态——全仓库 grep "tempo"/"zipkin" 无命中，pom.xml/application.yaml 均无相关依赖或配置，本文档"实现计划篇"是本次讨论后确定的设计方案，不是照抄现成代码。② 本文档的 maxDepth 可调设计、QueryTraceDTO 不含 service 字段这两点，与 UNIMPLEMENTED_FEATURES_REPORT.html 里最初的建议（固定深度 3、DTO 含 service 并接入 CMDB 校验）不同——差异原因见 深度不够怎么办 和 DTO/VO 两节，是这次讨论后主动调整的，不是遗漏。

1讲解篇

类比Tempo/Zipkin 是什么：调用链专用的"快递档案系统"

Tempo 是 Grafana 出的开源调用链存储与查询系统，跟 Prometheus（存 metric）、Loki（存 log）是同一套"可观测性三件套"里专门管 trace 的那一件；Zipkin 是另一套更早期的同类系统（Twitter 出品），定位几乎一样，只是实现和生态不同——这也是为什么规格里写"Tempo/Zipkin"，具体选哪个是部署侧的事，网关对接的编排模式是一样的。

生活类比 Tempo 就像快递公司给每个运单号建的档案袋：档案袋里按"父子关系"把这一单经过的每一段运输记录整整齐齐串好；你报一个单号，直接拿到整条链路，不用自己去各网点现场拼。它做的事情很单一——接收各服务上报的 span、按 traceId 存起来、支持按 traceId 查出整条链路，不做数据采集本身。

正因为它和 Prometheus/Loki 是"同一套体系里分工不同的一员"，query_trace 的网关侧代码结构（初始化带超时的 RestClient、先消费预算再请求上游、上游异常复用 GlobalExceptionHandler 降级分支）依然可以照抄 MetricsController 的模子。

概念span 从哪来：跟日志是两条完全独立的通路

用一个具体例子建立画面：一次下单请求经过 网关 A → 订单服务 B → 数据库 C 三跳，整趟旅程是 1 个 trace。里面 A 处理请求算 1 个 span，B 处理请求算另 1 个 span，B 查数据库这一下动作又算第 3 个 span——span = "某个服务/某段代码干的一件具体事"，一趟请求经过几跳、发生几次子调用，就有几个 span。

这些 span 是怎么产生的：A、B 这些服务的代码里都嵌了一小段"打点"逻辑（tracing SDK，通常是 OpenTelemetry SDK），每次干活前后自动记一笔"我是谁、干了多久、是被谁叫来的"，直接通过网络把这一笔发给 Tempo——不写进日志文件，是单独发出去的一条通路，跟"写日志 → 被 Promtail/Fluentd 采集 → 存进 Loki"完全是两条不同的路径。

类比为什么不能把 span 塞进 Loki 里存

span 记录看起来也是"一条带时间戳的数据"，跟日志行很像，但两者需要的查询方式完全不同：span 之间有严格的父子关系（parent_id 指向谁调用了谁），查询时必须把同一个 traceId 下的所有 span 拼回一棵树、按时间对齐算出"哪一跳耗时最长"。如果用纯文本存储做这件事，相当于每次查询都要在文本堆里现场做一遍"关系型 JOIN + 树重建"，效率很差；Tempo 从存储结构上就是按 traceId 索引、父子指针是结构化字段，专门为"拼树"优化过。

类型数据形态回答的问题本项目对应工具
metric（指标）数字随时间变化的曲线"现在/过去这个数值是多少、正常吗"query_metrics（已实现）
log（日志）一行行带时间戳的自由文本"当时具体发生了什么事、报了什么错"（WHAT）query_logs（未实现，另有文档）
trace（调用链）结构化的 span 树，只有骨架信息，无自由文本"卡在哪一跳、这一跳耗时多久"（WHERE + HOW LONG）query_trace（本文档主题）

span 里不存具体业务文本（比如"库存不足，sku=A1003"这种内容），只有服务名、起止时间、耗时、几个简单 tag——这是为了保持轻量、撑住海量并发。所以 trace 和 log 从不是互相替代关系：trace 告诉你 WHERE + HOW LONG，log 告诉你 WHAT，两者配合着用。

概念查询方式的本质区别：点查 vs 范围扫描

query_trace 不再是"划一个时间窗口、扫一段范围"，而是拿 traceId 直接做一次精确命中查询，这跟 query_metrics/query_logs 在查询形状上是本质不同的两类操作。

生活类比 query_metrics/query_logs 像"翻某段时间的监控记录本"——不知道异常具体发生在哪一秒，只能划定时间窗口把这段范围内的数据全部扫出来。query_trace 更像"拿着一个具体的快递单号去官网查物流"——不需要告诉系统"大概是这几天寄的"，单号本身就是索引，直接命中，一步到位。这也是为什么 Tempo 的核心查询接口是 GET /api/traces/{traceId}，压根不需要 start/end 参数，跟 Prometheus/Loki 的 query_range 形成鲜明对比。

对照代码traceId 从哪来：与 query_logs 的衔接

这条链路的主路径是先 query_logs、再 query_trace：investigate agent 先调 query_logs 拿到聚合结果，顺手拿到一批去重的 traceId，挑一个可疑的传给 query_trace 查完整调用链。这不是推测——query_logs 设计文档里 QueryLogsVO.distinctTraceIds 字段的原始注释就写着：

@Schema(description = "本次窗口内提取到的全部去重 traceId，可直接作为 query_trace 的入参")
private List<String> distinctTraceIds;

出处：query_logs-guide.html 的 QueryLogsVO 一节。少数情况下 traceId 也可能来自别的渠道（比如工单里用户报错时系统自带的），但本项目里唯一"官方"的获取路径就是 query_logs 的输出——这也是这两个模块要放进排障链路相邻两环来理解的原因：一个的出参就是另一个的入参。

概念span 树长什么样：Tempo 给的是扁平列表，网关自己拼树

Tempo 吐给网关的，是这一个 traceId 下所有 span 组成的一个平铺数组，每个 span 大概长这样（简化示意，字段用协议惯用的 snake_case）：

[
  {span_id: "s1", parent_id: null, service: "gateway",    duration_ms: 320},
  {span_id: "s2", parent_id: "s1",  service: "order-svc",  duration_ms: 280},
  {span_id: "s3", parent_id: "s2",  service: "db",          duration_ms: 250},
  {span_id: "s4", parent_id: "s2",  service: "cache",       duration_ms: 5}
]

parent_id 就是"这一段是谁叫起来的"，跟前面讲过的"运单流水号 + 上一段是谁"完全对应。网关拿到这个平铺列表后，需要自己按 parent_id 把它们拼回一棵树（s1 是根，s2 是 s1 的孩子，s3/s4 是 s2 的孩子），拼出来长这样：

gateway (s1, 320ms)
└── order-svc (s2, 280ms)
    ├── db (s3, 250ms)      ← 耗时占大头，一眼看出瓶颈在这
    └── cache (s4, 5ms)

这一步跟 query_logs 里的"pattern 聚合"是同一类工作——上游给的是原始碎片（扁平 span 列表 / 逐行日志），网关负责加工成结构化的东西再交给 agent。

类比为什么要做"深度 ≤3 精简"

一个真实生产环境的调用链，可能有几十上百个 span，嵌套 6-10 层深（网关→鉴权→订单→库存→缓存→数据库→…）。如果把整棵树原封不动转成 JSON 甩给 agent，跟 query_logs 里"把 3000 行原始日志直接甩过去"是同一个坑——直接打爆 agent 的上下文窗口。

类比：query_logs 的 pattern 聚合 pattern 聚合是"把几千行长得像的日志压缩成几条模式摘要"；深度裁剪是"把几十上百个 span 压缩成前几层的骨架视图"——动机完全一样：先给 agent 一个"够用但不过量"的概览，而不是把原始全量甩过去。

所以设计上只保留浅层结构（默认前 3 层，看清"大致走了哪几个服务、哪一层耗时突出"），深层子树折叠/丢弃，并在返回结构里标记发生了裁剪，让 agent 知道"这不是全貌"。

设计决策深度不够怎么办：maxDepth 可调 + 硬上限

如果固定死"只能看 3 层"，遇到瓶颈恰好在第 5 层的场景，agent 会拿到一个"看不出问题在哪"的截断结果——这是一个真实的设计权衡点，不是靠猜一个"更好的固定数字"（比如改成 3-6）能解决的。

本文档采用的方案：默认给小的（3 层），需要时 agent 自己主动要更多，但网关设硬上限兜底：

  • investigate agent 第一次查，不传深度参数，拿到默认 3 层的"概览"。
  • 如果发现某个分支被截断、且这个分支恰好是耗时最长的那个，agent 可以用同一个 traceId、加大 maxDepth（比如传 6）再查一次，专门把那个分支看得更深。
  • 不做成"无限深度"，是因为总要有硬上限兜底，否则一个笨拙的 agent 可以一直加大深度直到打爆自己的上下文——跟 pattern 聚合限制模式组数、window 限制 @Max(86400) 是同一个防滥用逻辑。

把决定权交给调用方，网关只负责兜底,不是网关帮 agent 一次猜对——这是本文档相对最初报告"固定深度 3"建议的主动调整,具体字段设计见 QueryTraceDTO。

对照代码DTO/VO：为什么 QueryTraceDTO 反而比 metrics/logs 更简单

复习：DTO/VO 是什么 DTO 像你填的寄件面单（调用方传进来的东西），VO 像快递公司返的运单详情（网关要返回出去的东西）——两者都只是数据搬运容器，本身没有业务逻辑。

WindowQueryDTO（metrics）和 QueryLogsDTO（logs）都必须带 service + window，因为它们是"划范围扫描"：不圈定服务和时间范围，上游根本不知道该扫哪一段。而 query_trace 是点查——前面讲过，traceId 本身就是全局唯一索引,不需要 service 或时间窗口来"圈定范围"。

字段WindowQueryDTO / QueryLogsDTOQueryTraceDTO
service必填，圈定查询范围不需要——traceId 已经是精确索引
window / endOffsetSeconds必填，划定时间范围不需要——点查没有"范围"概念
核心入参service + window(+可选 pattern)仅 traceId(+可选 maxDepth)

这个对比本身就是"点查 vs 范围扫描"这一区别的直接印证：DTO 更简单不是偷懒，是查询形状决定的。也因为没有 service 字段，最初报告建议的"service 参数需查 CMDB 校验"这一步在 query_trace 里不适用，具体设计见 实现计划篇。

总览总体设计一览

新增包 com.silas.iris.toolgateway.trace，结构对齐 metrics/logs 包：

com.silas.iris.toolgateway.trace
├── controller/TraceController.java       POST /trace/query
├── model/dto/QueryTraceDTO.java          入参：traceId + 可选 maxDepth
├── model/vo/TraceTreeVO.java             出参：裁剪后的 span 树
├── model/vo/SpanRaw.java                 Tempo 原始扁平 span（仅内部使用，不对外返回）
├── constant/TraceQueryConstants.java     路径/默认深度/上限常量
└── utils/TraceTreeUtil.java              扁平列表 -> 拼树 -> 按 maxDepth 裁剪

调用编排顺序（和 MetricsController.query() 同构）：消费预算 → 请求 Tempo 拿原始 span 列表 → 网关内拼树+裁剪 → 封装 ApiEnvelope。

代码QueryTraceDTO

package com.silas.iris.toolgateway.trace.model.dto;

import com.silas.iris.toolgateway.trace.constant.TraceQueryConstants;
import io.swagger.v3.oas.annotations.media.Schema;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Positive;
import lombok.Data;

@Data
public class QueryTraceDTO {

    @NotBlank
    @Pattern(regexp = "^[a-f0-9]{16,32}$", message = "traceId 格式不合法")
    @Schema(description = "调用链唯一标识，通常来自 query_logs 返回的 distinctTraceIds",
            example = "4bf92f3577b34da6a3ce929d0e0e4736", requiredMode = Schema.RequiredMode.REQUIRED)
    private String traceId;

    @Positive(message = "maxDepth 必须大于 0")
    @Max(value = TraceQueryConstants.MAX_DEPTH_LIMIT, message = "maxDepth 不能超过 " + TraceQueryConstants.MAX_DEPTH_LIMIT)
    @Schema(description = "返回的调用链树最大深度；不传则使用默认值 3，超出的子树会被裁剪",
            example = "3")
    private Integer maxDepth;
}

traceId 的校验正则 ^[a-f0-9]{16,32}$ 故意与 query_logs 里 TraceIdExtractor 提取出的格式对齐（见 LogsQueryConstants.TRACE_ID_PATTERN）——这样 query_logs 吐出来的 distinctTraceIds 才能直接喂给这个 DTO，不需要中间转换。没有 service 字段，原因见讲解篇。

代码TraceTreeVO

package com.silas.iris.toolgateway.trace.model.vo;

import io.swagger.v3.oas.annotations.media.Schema;
import lombok.*;
import java.util.List;

@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
@Schema(description = "调用链树（裁剪后）")
public class TraceTreeVO {

    @Schema(description = "调用链唯一标识")
    private String traceId;

    @Schema(description = "裁剪前该 trace 下的 span 总数")
    private int totalSpanCount;

    @Schema(description = "本次实际生效的裁剪深度")
    private int appliedMaxDepth;

    @Schema(description = "裁剪后的树根节点")
    private SpanNode root;

    @Data
    @Builder
    @NoArgsConstructor
    @AllArgsConstructor
    @Schema(description = "单个 span 节点")
    public static class SpanNode {

        @Schema(description = "span 唯一标识")
        private String spanId;

        @Schema(description = "该 span 所属服务名")
        private String service;

        @Schema(description = "操作名，如 HTTP 方法+路径、SQL 摘要")
        private String operationName;

        @Schema(description = "该 span 耗时，单位毫秒")
        private long durationMs;

        @Schema(description = "子 span 列表，深度超过 maxDepth 时为空列表")
        private List<SpanNode> children;

        @Schema(description = "该节点因深度裁剪被丢弃的直接子孙数量；0 表示未发生裁剪")
        private int prunedChildCount;
    }
}

全局 ApiEnvelope.Meta.truncated 的取值：只要树里存在任意一个 prunedChildCount > 0 的节点，就设为 true——语义上与 query_logs 的 truncated 信号完全一致（"精简结果不是全貌"）。totalSpanCount 对照 QueryLogsVO.totalLines 的设计目的：让 agent 直观感受到"这次帮你省了多少信息"。

代码TraceController 骨架

@Slf4j
@RestController
@RequestMapping("/trace")
@Validated
@Tag(name = "Trace 查询", description = "封装 Tempo 按 traceId 查询接口，返回深度裁剪后的调用链树")
public class TraceController {

    private final RedisService redisService;
    @Value("${iris.tempo.base-url}") private String tempoBaseUrl;
    @Value("${iris.tempo.connect-timeout-ms:3000}") private int connectTimeoutMs;
    @Value("${iris.tempo.read-timeout-ms:10000}") private int readTimeoutMs;
    private RestClient tempoClient;

    public TraceController(RedisService redisService) {
        this.redisService = redisService;
    }

    @PostConstruct
    void initTempoClient() {
        // 与 MetricsController#initPrometheusClient 同构：显式设超时，
        // 否则 Tempo 挂起时线程会无限期占用，degraded 分支永远等不到异常抛出
        SimpleClientHttpRequestFactory requestFactory = new SimpleClientHttpRequestFactory();
        requestFactory.setConnectTimeout(connectTimeoutMs);
        requestFactory.setReadTimeout(readTimeoutMs);
        this.tempoClient = RestClient.builder()
                .baseUrl(tempoBaseUrl)
                .requestFactory(requestFactory)
                .build();
    }

    @PostMapping("/query")
    public ApiEnvelope<TraceTreeVO> query(
            @Valid @RequestBody QueryTraceDTO dto,
            @RequestAttribute(HeaderConstants.INCIDENT_ID_ATTR) String incidentId,
            HttpServletRequest request) {

        long startTask = System.currentTimeMillis();
        request.setAttribute(HeaderConstants.TOOL_NAME_ATTR, AuditConstants.QUERY_TRACE); // 需新增常量
        request.setAttribute(HeaderConstants.TEMPLATE_OR_RAW_ATTR, AuditConstants.TEMPLATE);
        request.setAttribute(HeaderConstants.AUDIT_REQUEST_PARAMS_ATTR, BeanUtil.beanToMap(dto));

        // 1. 限流：见下方"复用现有横切机制"一节的预算共享决策
        Long remaining = redisService.consume_tool_calls(incidentId);

        // 2. 请求 Tempo，拿到该 traceId 下的原始扁平 span 列表
        int maxDepth = Objects.requireNonNullElse(dto.getMaxDepth(), TraceQueryConstants.DEFAULT_MAX_DEPTH);
        List<SpanRaw> rawSpans = fetchTrace(dto.getTraceId());

        // 3. 网关内加工：按 parent_id 拼树，再按 maxDepth 裁剪
        TraceTreeVO data = TraceTreeUtil.buildAndPrune(dto.getTraceId(), rawSpans, maxDepth);

        return ApiEnvelope.ok(data, buildMeta(startTask, remaining, data));
    }

    // fetchTrace() 用 tempoClient.get().uri(TraceQueryConstants.QUERY_TRACE_PATH, traceId)
    //   .retrieve().body(new ParameterizedTypeReference<List<SpanRaw>>() {})，
    //   与 MetricsController#fetchQueryRange 同构；
    // buildMeta() 根据 data 中是否存在 prunedChildCount > 0 的节点设置 truncated
}

Tempo 真实的 GET /api/traces/{traceId} 响应结构比这里的示意复杂（嵌套 resourceSpans/scopeSpans，遵循 OTLP 协议），fetchTrace 内部需要先做一层"协议解析 -> 拍平成 SpanRaw 列表"的转换，具体字段映射建议实现时对照 Tempo HTTP API 文档 逐字段核对，不在本文档展开。

代码TraceTreeUtil：拼树 + 深度裁剪

package com.silas.iris.toolgateway.trace.utils;

public final class TraceTreeUtil {
    private TraceTreeUtil() {}

    public static TraceTreeVO buildAndPrune(String traceId, List<SpanRaw> rawSpans, int maxDepth) {
        Map<String, List<SpanRaw>> childrenByParent = rawSpans.stream()
                .filter(s -> s.getParentId() != null)
                .collect(Collectors.groupingBy(SpanRaw::getParentId));
        SpanRaw rootRaw = rawSpans.stream()
                .filter(s -> s.getParentId() == null)
                .findFirst()
                .orElseThrow(() -> new IllegalStateException("trace 缺少根 span: " + traceId));

        SpanNode root = pruneRecursive(rootRaw, childrenByParent, 1, maxDepth);

        return TraceTreeVO.builder()
                .traceId(traceId)
                .totalSpanCount(rawSpans.size())
                .appliedMaxDepth(maxDepth)
                .root(root)
                .build();
    }

    // depth 从 1 开始计（根节点算第 1 层）；到达 maxDepth 且仍有子节点时，
    // 保留当前节点本身，但子节点整体丢弃，记录被丢弃的数量
    private static SpanNode pruneRecursive(SpanRaw current,
            Map<String, List<SpanRaw>> childrenByParent, int depth, int maxDepth) {
        List<SpanRaw> childRaws = childrenByParent.getOrDefault(current.getSpanId(), List.of());

        if (depth >= maxDepth && !childRaws.isEmpty()) {
            return toNode(current, List.of(), childRaws.size());
        }
        List<SpanNode> children = childRaws.stream()
                .map(c -> pruneRecursive(c, childrenByParent, depth + 1, maxDepth))
                .toList();
        return toNode(current, children, 0);
    }

    private static SpanNode toNode(SpanRaw raw, List<SpanNode> children, int prunedChildCount) {
        return SpanNode.builder()
                .spanId(raw.getSpanId())
                .service(raw.getService())
                .operationName(raw.getOperationName())
                .durationMs(raw.getDurationMs())
                .children(children)
                .prunedChildCount(prunedChildCount)
                .build();
    }
}

这版实现假设一个 trace 只有 1 个根 span（parent_id == null）——真实数据里偶尔会出现"孤儿 span"（parent_id 指向一个不存在于返回列表里的 span，常见于采样丢失）或"多根"的异常情况，实现时需要补一层防御：找不到根就按"取时间最早的 span 当根"兜底，而不是直接抛异常导致整个查询失败。

需要你拍板复用现有横切机制（含预算是否共享）

  • 鉴权：AuthInterceptor 用 addPathPatterns("/**") 全局注册，/trace/** 自动被覆盖，无需改动。
  • 上游降级：GlobalExceptionHandler 已有 ResourceAccessException/HttpServerErrorException.ServiceUnavailable → 200 degraded 的映射，Tempo 超时/不可达自动走这条路径，前提是 initTempoClient() 显式设置了 connect/read timeout。
  • 审计常量：AuditConstants 目前只有 QUERY_METRICS，需要新增 QUERY_TRACE = "query_trace"。
  • service 校验：前面讲过，query_trace 没有 service 字段，这一步不适用，与最初报告的建议不同。
需要你决定的一件事：预算是否共享 RedisService.consume_tool_calls(incidentId) 是模板通道共用的 30 次/24h 配额，query_metrics 已在用；如果 query_logs、query_trace 都直接调用同一个方法，三个工具会共用同一份 30 次配额，而不是各自 30 次。

A）共享预算（推荐，与 query_logs 文档保持一致的默认选择，改动最小）：语义是"模板通道总预算 30 次"，不区分具体是哪个工具。
B）独立预算：仿照 consume_raw_tool_calls，新增 consume_trace_tool_calls(incidentId) + 独立 key/限额。

建议先用 A 上线，如果实测发现 investigate agent 一次排障要跑 metrics+logs+trace 好几轮、30 次很快耗尽，再切换成 B——这个信号只有跑起来才能观察到，现在没必要预先优化。
